Ошибки и отладка

Где искать, почему упало, и как сделать workflow устойчивым.

Основная идея урока

Ошибки в автоматизации — норма, а не катастрофа. n8n показывает, на какой ноде остановилось и с каким сообщением, показывает сохранённые запуски во вкладке Executions и даёт настройки: повторить попытку, продолжить несмотря на ошибку, сообщить об ошибке отдельным workflow.

Как выглядит ошибка

Упавшая нода получает красную рамку и значок «!». Выполнение останавливается на ней: ноды справа не запускаются. Откройте ноду: в панели OUTPUT вместо данных будет красный блок с сообщением. Читайте его целиком, обычно там написано, что именно не так.

Порядок действий всегда один:

  1. Найти красную ноду на холсте.
  2. Открыть её и прочитать сообщение об ошибке целиком.
  3. Посмотреть, что реально подставилось: строка Result под полем с выражением.
  4. Сравнить с панелью INPUT: есть ли такое поле, так ли оно называется.
  5. Исправить и нажать Execute step.
  6. Убедиться, что в OUTPUT появились данные.
  7. Запустить весь workflow целиком.
ТренажёрЗапустите workflow кнопкой Execute workflow. Найдите упавшую ноду, откройте её, разберитесь по строке Result, что не так, исправьте и добейтесь успешного запуска всей цепочки.
Проверьте себя
Нода HTTP Request упала с 404, а в её URL есть выражение. С чего начать?
  • Посмотреть строку Result под полем URL
  • Удалить ноду и добавить её заново
  • Написать в поддержку сервиса про 404
  • Сменить метод запроса на POST

Вкладка Executions: история запусков

Рядом с Editor есть вкладка Executions. В ней список сохранённых запусков: время, статус (Success или Error), длительность, как запущен (вручную или триггером). Клик по запуску открывает его на холсте с данными каждой ноды, как будто вы запустили его сейчас. Так разбирают ошибки, случившиеся ночью.

ТренажёрНайдите в списке запуск со статусом Error и откройте его. Посмотрите, на какой ноде остановился workflow.
!
Pin data: не дёргать сервис каждый раз

В панели OUTPUT есть кнопка-булавка Pin. Она замораживает данные ноды: при следующих запусках n8n не будет выполнять её заново, а возьмёт закреплённые данные. Полезно при отладке: один раз получили ответ от API или вебхука, закрепили, и дальше настраиваете следующие ноды, не ожидая новых запросов. Перед публикацией булавки удобно снять: в реальной работе они не действуют, но путают.

Прогноз. Google Sheets «прочитать новые строки» не нашёл ни одной. Следующая нода Telegram должна написать менеджеру «новых заявок нет». Что она сделает?

Ничего. У Google Sheets ноль элементов на выходе, значит Telegram не получит ни одного и не выполнится ни разу: правило «по элементу» работает и в эту сторону, ноль элементов — ноль действий. Workflow тихо закончится без сообщения. Чтобы сообщение всё-таки ушло, у Google Sheets включают Always Output Data: она отдаст один пустой элемент, и Telegram сработает. Эта настройка есть в таблице ниже.

Настройки устойчивости: вкладка Settings

У каждой ноды есть вкладка Settings с одинаковым набором переключателей. Три из них спасают от большинства ночных падений.

НастройкаЧто делаетКогда включать
Retry On FailПри ошибке повторяет попытку: сколько раз (Max Tries) и через сколько (Wait Between Tries)Для любых обращений к внешним сервисам: сеть и API иногда моргают
On Error → ContinueНе останавливать workflow, идти дальше с тем, что естьКогда шаг не критичен: не отправилось одно уведомление, остальное должно работать
On Error → Continue (using error output)У ноды появляется второй выход «error», куда уходят упавшие элементыКогда ошибки нужно обрабатывать отдельно: записать, сообщить
Always Output DataВернуть пустой элемент, даже если результата нетGoogle Sheets не нашёл новых строк. Без этой настройки цепочка на нём остановится, с ней следующая нода всё равно отправит «новых заявок нет»

Error Workflow: узнать об ошибке первым

Когда workflow падает ночью, никто не узнает, пока не заглянет в Executions. Решение: отдельный workflow с триггером Error Trigger и нодой Telegram. В настройках основного workflow (⋯ → Settings → Error Workflow) выберите его. В ноде Telegram настройте текст с данными ошибки. Для проверки вызовите ошибку автоматическим триггером: ручной запуск из редактора не вызывает Error Trigger. Делать отдельный «сторож» для каждого workflow не нужно: в настройках каждого выбирайте один и тот же.

Error Trigger → Сообщить админу

Весь Error Workflow: две ноды. Срабатывает, когда автоматический запуск подключённого workflow завершился ошибкой.

Что вы теперь умеете

  • Находить упавшую ноду и читать сообщение об ошибке целиком.
  • Сверять строку Result с панелью INPUT и чинить имя поля.
  • Открывать ночной запуск в Executions и включать Retry On Fail там, где сервис моргает.

Подумайте о своём: какая нода в вашей автоматизации скорее всего упадёт ночью? Обычно та, что ходит во внешний сервис. Как вы узнаете об этом первым? Ответ из этого урока: Error Workflow с Telegram.

Workflow Settings: что ещё там есть

Меню «⋯» → Settings в редакторе. Кроме Error Workflow и Timezone там есть: Save successful executions и Save failed executions (хранить ли историю), Save manual executions (хранить ли ручные запуски), Timeout (прервать слишком долгий запуск). Для начала оставьте всё по умолчанию, но знайте, где это лежит.

Итог урока

Главная мысль: Ошибка — красная нода с сообщением. Читаем сообщение, смотрим Result и INPUT, чиним, проверяем Execute step. История в Executions, устойчивость через Retry On Fail и On Error, уведомления через Error Workflow.

  • При настройке Stop Workflow ошибка останавливает выполнение. Режим Continue позволяет продолжить работу.
  • Состав истории зависит от настроек сохранения и срока хранения.
  • Pin замораживает данные ноды для отладки.
  • Error Trigger может сообщить о сбое автоматического запуска.
Проверка знаний
1. Workflow упал ночью. Где посмотреть, на какой ноде и с какими данными?
  • Во вкладке Executions, открыв нужный запуск
  • В разделе Credentials рядом с ключами
  • В настройках workflow, пункт Error Workflow
  • Нигде: данные ночных запусков не хранятся
2. Нода обращается к сервису, и раз в день сервер случайно не отвечает. Какая настройка поможет?
  • Always Output Data
  • Retry On Fail
  • Execute Once
  • Pin data
3. Вы настраиваете ноду после Webhook, и для каждой проверки приходится заново отправлять форму с сайта. Что сделать, чтобы не отправлять?
  • Закрепить OUTPUT ноды Webhook булавкой Pin
  • Включить Always Output Data в настройках Webhook
  • Опубликовать workflow
  • Поставить Retry On Fail на Webhook
4. Как получать сообщение в Telegram, если автоматический запуск завершился ошибкой?
  • Error Workflow с Error Trigger → Telegram
  • Нода Telegram в конце основного workflow
  • Retry On Fail на каждой ноде с уведомлением
  • Always Output Data на последней ноде
5. В выражении {{ $json.body.name }} получилось [undefined], а в INPUT поле name лежит в корне элемента. В чём дело?
  • Поле лежит в корне, нужно {{ $json.name }}
  • Нужно сначала опубликовать workflow
  • Выражения не работают с полем name
  • Сервер не вернул поле body
6. При ошибке в ноде уведомления остальная часть workflow должна выполниться. Что выбрать в Settings ноды?
  • On Error → Stop Workflow
  • On Error → Continue
  • Execute Once
  • Retry On Fail с нулём попыток
7. Повторение. Менеджер жалуется: заявка на 900 рублей «пропала», ошибок в Executions нет. В workflow стоит If «amount больше 1000». Где искать заявку?
  • Во вкладке false ноды If
  • Во вкладке true ноды If
  • В Error Workflow
  • В панели INPUT ноды Webhook
8. Повторение. HTTP Request раз в день падает с 429 Too Many Requests. Что это значит и что сделать?
  • Слишком часто: включить Batching или Retry с паузой
  • Неверный адрес: сверить URL с документацией сервиса
  • Нет ключа доступа: выбрать credential
  • Сервер сломался: написать в поддержку
