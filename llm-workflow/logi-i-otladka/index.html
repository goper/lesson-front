Логи и отладка: как найти сломанный шаг

Писать в логи то, по чему потом получится восстановить путь одного запуска и найти первое место, где всё пошло не так.

Одна строка в логах

Пользователь пишет, что цепочка создала неправильный тикет. Вы открываете логи и находите там ровно одну строку:

ERROR: generation failed

Дальше идти некуда. Непонятно, какой это был запуск, на каком шаге сломалось, был ли повтор, какие данные пришли на вход и что ответила модель. Каждый сервис по отдельности выглядит исправным, по метрикам всё зелено.

Многошаговая цепочка умеет заканчиваться неправильным результатом без единой аварии внутри. Данные изменились на промежуточном шаге, модель получила не ту версию промпта, повтор отработал дважды, внешний API отдал не то на последнем шаге. Сообщения workflow failed для разбора такого недостаточно.

Главная мысль

Отладка требует возможности восстановить историю конкретного запуска: какие данные пришли, какие шаги выполнялись, сколько заняли и что каждый передал дальше.

Простыми словами

Бортовой самописец в самолёте пишет не «полёт не удался», а каждый параметр по времени: высоту, скорость, положение рулей. Разбор после инцидента идёт по этой ленте от конца к первому отклонению. Логи цепочки должны быть такой лентой для одного запуска.

Что записывать по каждому шагу

Отдельный запуск нужно уметь опознать. Один и тот же workflow порождает десятки запусков, и без идентификатора запуск не найти. В распределённой системе один запрос ещё и проходит через несколько сервисов, поэтому рядом с идентификатором запуска живёт trace ID: сквозной идентификатор одной логической операции через все компоненты.

Запись шага отвечает на шесть вопросов: какой запуск, какой шаг, когда начался, сколько выполнялся, чем закончился и была ли это повторная попытка. Из них получается базовый набор полей.

Базовые поля любого шага

execution_id   какой запуск
trace_id       какая логическая операция
step_name      какой шаг
start_time     когда начался
duration       сколько выполнялся
status         чем закончился
attempt        номер попытки
error_type     вид ошибки, если была

Поля шага с моделью (добавляются)

model                    имя и версия модели
prompt_version           версия инструкции
input_tokens             расход на вход
output_tokens            расход на выход
latency                  задержка ответа
structured_output_valid  прошёл ли ответ схему
(для агента ещё: инструмент, аргументы,
 статус результата, число ходов)

Смысл структурированного логирования именно в отдельных полях. По одной длинной строке ни отфильтровать, ни посчитать: по step_name не найти все ошибки конкретного шага, а по duration не выбрать медленные запуски.

Подсказка

Особняком стоит версия промпта. Без неё нельзя понять, связано ли изменение поведения модели с новой инструкцией или с чем-то ещё, и разбор превращается в гадание. Достаточно короткого идентификатора вроде хеша или номера, лишь бы он менялся вместе с текстом.

Структурированный лог: контекст запуска в каждой записи
<?php
// Структурированный лог: Monolog пишет JSON, процессор добавляет execution_id и trace_id в каждую запись.
use Monolog\Attribute\AsMonologProcessor;
use Monolog\LogRecord;
use Psr\Log\LoggerInterface;

#[AsMonologProcessor]
final class RunContextProcessor
{
    public function __construct(private RunContext $ctx) {}   // execution_id и trace_id текущего запуска

    public function __invoke(LogRecord $record): LogRecord
    {
        $record->extra['execution_id'] = $this->ctx->executionId;
        $record->extra['trace_id']     = $this->ctx->traceId;
        return $record;
    }
}

// В шаге пишем поля, а не предложение:
$logger->info('step', ['step_name' => 'load_pr', 'status' => 'ok', 'duration_ms' => 120, 'attempt' => 1]);
$logger->info('step', ['step_name' => 'call_model', 'status' => 'ok', 'duration_ms' => 2400, 'attempt' => 1,
    'model' => 'yandexgpt/latest', 'prompt_version' => 'v14',
    'input_tokens' => 1830, 'output_tokens' => 210, 'structured_output_valid' => true]);
$logger->error('step', ['step_name' => 'create_ticket', 'status' => 'error', 'duration_ms' => 3005,
    'attempt' => 2, 'error_type' => 'timeout']);

// config/packages/monolog.yaml → handlers.main.formatter: monolog.formatter.json
// Каждая запись станет одной JSON-строкой с отдельными полями.

Чего в логах быть не должно

Полный вход и выход модели для отладки бесценны: без них непонятно, почему модель приняла именно такое решение. Ровно поэтому правило «всегда логируйте весь промпт и весь ответ» звучит соблазнительно, и ровно поэтому оно опасно. В промпт попадают персональные данные, внутренние документы, сообщения пользователей, коммерчески чувствительная информация, а при неудачной архитектуре и токены доступа. Логи при этом обычно живут дольше, хранятся в другой системе и доступны более широкому кругу людей, чем сами данные.

Главная мысль

Наблюдаемость не должна становиться новым каналом утечки.

Решение о хранении содержимого принимается по политике данных приложения, а инструменты стандартные: вымарывание чувствительных фрагментов, маскирование персональных данных, ограничение доступа, короткий срок хранения и запись версии промпта вместо его полного текста.

Маскирование перед записью: почта, телефон, токены
<?php
// Маскирование перед записью в лог: почта, телефон, ключи. Лог не должен стать каналом утечки.
function maskPii(string $text): string
{
    // i***@example.com
    $text = preg_replace_callback('/[\w.+-]+@[\w-]+\.[\w.]+/u',
        fn (array $m) => mb_substr($m[0], 0, 1) . '***@' . explode('@', $m[0])[1], $text);
    // телефоны с любыми разделителями: 8 (912) 345-67-89, +7 912 345 67 89
    $text = preg_replace('/(?:\+7|8)[\s(]*\d{3}[\s)-]*\d{3}[\s-]*\d{2}[\s-]*\d{2}/u', '+7 *** *** ** **', $text);
    // ключи API по характерным префиксам
    return preg_replace('/\b(?:AQVN|sk-|ya29\.)[A-Za-z0-9_-]{8,}/', '[token]', $text);
}

$prompt = 'Клиент Иван Петров, ivan.petrov@example.com, 8 (912) 345-67-89, ключ AQVNabcdef123456 — не работает оплата';
echo maskPii($prompt), PHP_EOL;
Имя клиента регулярка не поймает: для имён нужны либо словари, либо отдельная модель-детектор, либо решение хранить текст только ограниченный срок с ограниченным доступом.

Как искать причину

Отлаживать мысли модели не нужно и невозможно. Внутренними вычислениями модели у провайдера вы не управляете так, как своей функцией. Для инженерного разбора этого и не требуется: важны наблюдаемые границы. Какой вход пришёл, какой контекст добавился, какая версия промпта использовалась, какая модель была вызвана, какой ответ получен, какая проверка сработала, какое действие выполнилось дальше. Эта последовательность и показывает, где сломалось: в данных, в оркестрации, в вызове модели или во внешнем инструменте.

Главная мысль

Разбор идёт от результата к причине, а не от промпта. Сначала по идентификатору находится конкретный запуск. Дальше по шагам сверху вниз ищется первое место, где фактическое состояние разошлось с ожидаемым.

Повторы проверяются отдельно. Один запуск мог содержать несколько попыток одного шага, и вполне возможно, что первая фактически выполнила внешнее действие, а вторая создала дубликат. Для изменяющих операций поэтому нужны число попыток, идентификатор операции и идентификатор созданного внешнего объекта.

Найденный случай сохраняется. Минимум входных данных, на котором проблема воспроизводится, с вычищенными секретами. Разовый инцидент превращается в регрессионный случай, который потом уходит в оценочный набор (следующий урок), и та же поломка не возвращается после следующей правки.

Подсказка

Полезный сигнал дают и цифры расхода. Резкий рост input_tokens, числа итераций агента или количества вызовов инструментов означает, что цепочка либо набрала лишнего контекста, либо зациклилась. Эти поля нужны не только для учёта денег.

В Yandex Workflows: история выполнения

История запуска в Yandex Workflows отдаёт как раз то, что нужно для такого разбора: идентификатор и тип шага, время начала, длительность, статус, вход, ответ, информацию об ошибке, число попыток и последнюю ошибку после исчерпания повторов. Наличие входов и выходов в этой истории не отменяет требований к защите чувствительных данных: токен бота, попавший в адрес HTTP-шага, окажется и в истории запуска.

Отладка и оценка качества это разные занятия

Отладка отвечает, почему конкретный запуск завершился неправильно. Оценка отвечает, насколько хорошо система работает на представительном наборе сценариев. Один плохой ответ разбирается трассой и промптом, но вывод «новая модель хуже старой» из него не следует: для такого вывода нужны оценочный набор и систематический прогон по нему. Об этом следующий урок.

Главное

Логировать всё подряд плохая стратегия: чем больше данных, тем труднее найти сигнал, дороже хранение и выше риск утечки. Поля выбираются под вопросы, на которые система должна уметь ответить. Почему запуск упал? Почему он был медленным? Почему модель получила такой контекст? Какой инструмент был вызван? Сколько было повторов? С какой версией промпта получен результат?

Главная мысль

Минимальный полезный набор: идентификатор запуска и трассы, шаг, время, статус, число попыток и ошибка. Для модели добавляются её имя, версия промпта, задержка и расход токенов. Для агента ещё вызовы инструментов и число ходов. Цель одна: восстановить по логам цепочку «вход → шаги → вызовы модели → повторы → проверки → результат». Всё остальное в логах либо помогает её восстановить, либо там лишнее.

Самостоятельная работа: запись, по которой чужой человек восстановит запуск
  1. Заведите сквозной идентификатор. Убедитесь, что он появляется в самом начале, проходит через все шаги и попадает в каждую запись.
  2. Опишите запись одного шага: идентификатор запуска, имя шага, время начала и длительность, статус, номер попытки, причина ошибки. Для модельного шага добавьте версию промпта, имя модели, расход токенов и пару промпт-ответ.
  3. Пройдите по полям и отметьте, что нельзя хранить целиком. Для каждого выберите одно из трёх: маскирование, хранение только признака, ограниченный срок хранения.
  4. Возьмите вымышленную жалобу «вчера ассистент ответил ерунду» и ответьте по своей записи: какой это был запуск, какие шаги выполнились, какой промпт ушёл, что вернулось, где разошлось с ожиданием.
  5. Превратите найденный случай в проверку: опишите, как этот вход попадёт в набор регрессионных случаев.
  • Сквозной идентификатор есть в каждой записи
  • В записи шага есть статус, номер попытки и длительность
  • Для модельного шага есть версия промпта, расход токенов и пара промпт-ответ
  • Для каждого чувствительного поля выбран способ защиты
  • По записи удалось ответить на все пять вопросов
  • Случай оформлен как регрессионная проверка

Проверьте себя

1. Единственная запись о сбое это строка ERROR: generation failed. Какого минимального набора полей не хватает, чтобы начать поиск?
  • Полный промпт, ответ модели и все документы из контекста
  • Загрузка воркеров и версия сервиса
  • Идентификатор запуска, шаг, статус, длительность, номер попытки и тип ошибки
  • Температура модели и стоимость вызова
2. Пользователь сообщает, что цепочка создала тикет с неверным проектом. Промпт менять пока не хотят. С чего начать разбор?
  • Сразу переписать промпт
  • Найти запуск по идентификатору и пройти по шагам от входа к результату, ища первое расхождение
  • Откатить модель
  • Увеличить число повторов
3. Команда решила логировать промпт и ответ целиком. В промпт попадают обращения клиентов и внутренние документы. Что спроектировано неверно?
  • Логов слишком мало
  • Логи становятся каналом утечки: нужны маскирование, ограничение доступа, срок хранения или версия промпта вместо текста
  • Промпт слишком длинный
  • Всё верно, так удобнее отлаживать
4. На один запрос во внешней системе появились два одинаковых счёта. Какие поля подтвердят, что виноват повтор шага, а не два разных запуска?
  • Температура и модель
  • Номер попытки, идентификатор операции и идентификатор созданного объекта внутри одного execution_id
  • Загрузка процессора
  • Версия промпта
5. После перехода на другую модель пришёл один плохой ответ. Инженер предлагает сразу откатить модель. Что корректнее?
  • Откатить и закрыть инцидент
  • Разобрать этот запуск по следам, а вывод «модель хуже» делать по оценочному набору, не по одному ответу
  • Увеличить температуру
  • Удалить лог
6. Зачем нужен trace_id, если есть execution_id?
  • Для красоты
  • Чтобы связать записи одной операции через разные компоненты: webhook, цепочку, функцию, внешний API
  • Чтобы считать токены
  • Это одно и то же
