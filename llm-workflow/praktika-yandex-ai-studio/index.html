Практика: цепочка в Яндекс AI Studio

Собрать в Yandex Workflows ежедневный дайджест для оператора поддержки: тикеты из YDB, статьи базы знаний через функцию-реранкер, сводка от модели, отправка в Telegram.

Практика собирает одну рабочую цепочку. Раз в день она читает из базы YDB тикеты за последние сутки, ищет подходящие статьи базы знаний, просит модель собрать из них сводку и отправляет результат оператору в Telegram. Сначала разберём, как устроен Yandex Workflows и зачем цепочке прослойка-функция, потом подготовим окружение, соберём цепочку по шагам и сделаем три задания.

  • Запуск: Триггер из урока 3. Расписание раз в день или ручной запуск кнопкой. Входных данных цепочке не нужно: она берёт их сама из базы, поэтому пустой JSON {} на входе это нормально.
  • Workflow (YaWL): Сама цепочка, описанная на языке YaWL. Шесть шагов: прочитать тикеты, проверить, что они есть, вызвать функцию-реранкер, вызвать агента для сводки, отправить сообщение, завершить. Состояние запуска это JSON, который каждый шаг пополняет.
  • Сервисы облака: То, к чему цепочка обращается внутри Яндекс Облака. База тикетов, функция-прослойка, два поисковых индекса с базой знаний и текстовый агент AI Studio, который пишет сводку.
  • Внешний мир: Доставка результата из урока 2: HTTP-запрос к Telegram, сообщение приходит оператору. Единственная часть за пределами облака.

Как устроен Yandex Workflows

Yandex Workflows это сервис Яндекс Облака, в котором цепочку описывают как набор шагов и переходов между ними. Собрать её можно в визуальном редакторе (узлы на холсте, стрелки задают порядок, клик по узлу открывает настройки) или текстом на языке YaWL в формате YAML. Логика та же, что в n8n или самописных системах оркестрации, различаются детали интерфейса.

`yawl`
Версия языка. Спецификация начинается с неё.
`start`
Имя первого шага.
`steps`
Сами шаги. Каждый с именем, типом и переходом next.
Интеграционные шаги
Обращаются к внешним системам: databaseQuery (запрос к YDB), httpCall (HTTP-запрос), aiStudioAgent (вызов агента).
Управляющие шаги
Решают, куда идти дальше: switch выбирает ветку по условию, success завершает запуск.
Состояние запуска
JSON, который начинается со входа запуска и пополняется результатом каждого шага.
`output`
Шаблон на языке jq, который говорит, что шаг добавит в состояние.
Простыми словами

jq это маленький язык для работы с JSON, как формулы в таблице. Точка . означает «текущие данные». .tickets достаёт поле tickets. Вертикальная черта | передаёт результат дальше, как труба: .tickets | length считает, сколько тикетов. В YaWL выражение, которое что-то кладёт в состояние, заворачивают в \( ... ), а условие пишут как есть.

Выражение jqЧто делает
.всё текущее состояние
.ResultSets[0]первая таблица из результата запроса к базе

Попробуйте Как состояние проходит через цепочку

Нажимайте «Следующий шаг» и смотрите, какой фрагмент YaWL выполняется и что появляется в состоянии. Галочка «тикетов нет» показывает ветку с ранним завершением.

Запуск стартует с входным JSON, и после него во вкладке «Запуски» остаётся история с входом, выходом, статусом и временем каждого шага. Запустить цепочку можно вручную кнопкой, а регулярный запуск задаётся расписанием в формате cron.

Главная мысль

Цепочка не зависит от того, передаст ли расписание входные данные: она берёт данные сама, из базы, и проверяет условие по тому, что вернул запрос. Поэтому один и тот же workflow одинаково работает и по кнопке с пустым входом, и по расписанию.

Зачем нужна прослойка-функция

Ограничение платформы такое: текстовый агент в AI Studio работает только с одним поисковым индексом, а запрос сразу к нескольким индексам поисковый инструмент отклоняет ошибкой 400. Обход стандартный: код-прослойка. Облачная функция принимает запрос, сама обходит все индексы, объединяет найденное и отдаёт результат, а цепочка обращается уже к ней. Заодно функция берёт на себя роль судьи, который выбирает лучшие фрагменты из найденного. Это задача реранкинга (переупорядочивания результатов поиска) в чистом виде.

Индексы функция не хранит в коде. Она находит их по метке reranker=true, поэтому новый источник знаний подключается созданием индекса с этой меткой, без правки кода и нового развёртывания. Каждый индекс опрашивается отдельным вызовом, потому что за один вызов платформа принимает один индекс, и делается это параллельно.

Ядро функции: параллельный опрос, удаление дублей, судья с повтором и запасным путём
<?php
// Функция reranker: опросить все индексы параллельно, убрать дубли, попросить судью упорядочить, вернуть top_k.
final class Reranker
{
    public function __construct(private HttpClientInterface $search, private Judge $judge) {}

    /** @return list<array{text: string, source_index: string, hash: string}> */
    public function retrieveFromIndexes(string $query, array $indexIds, int $topKPerIndex): array
    {
        // HttpClient отправляет запросы параллельно: сначала создаём все, потом читаем ответы
        $responses = [];
        foreach ($indexIds as $id) {
            $responses[$id] = $this->search->request('POST', '/search', [
                'json' => ['index_id' => $id, 'query' => $query, 'top_k' => $topKPerIndex],
            ]);
        }
        $chunks = [];
        foreach ($responses as $id => $response) {
            try {
                foreach ($response->toArray()['results'] as $hit) {
                    $chunks[] = ['text' => $hit['text'], 'source_index' => $id];
                }
            } catch (\Throwable $e) {
                error_log("RETRIEVAL_WORKER_ERROR index=$id {$e->getMessage()}");   // один индекс упал, остальные работают
            }
        }
        $seen = []; $deduped = [];                                     // дубли по хешу первых 500 символов
        foreach ($chunks as $c) {
            $h = sha1(mb_substr($c['text'], 0, 500));
            if (isset($seen[$h])) continue;
            $seen[$h] = true; $c['hash'] = $h; $deduped[] = $c;
        }
        error_log(sprintf('RETRIEVAL_TOTAL raw=%d deduped=%d', count($chunks), count($deduped)));
        return $deduped;
    }

    /** @return array{0: list<array>, 1: bool} отсортированный top-K и флаг, сработал ли судья */
    public function rerank(string $query, array $candidates, int $topK, int $maxRetries = 2): array
    {
        if (count($candidates) <= 1) return [array_slice($candidates, 0, $topK), false];

        $system = Prompts::SYSTEM_JUDGE; $lastError = null;
        for ($attempt = 0; $attempt <= $maxRetries; $attempt++) {
            try {
                $raw     = $this->judge->call($system, Prompts::buildUserPrompt($query, $candidates));
                $ranking = Prompts::parseRanking($raw, count($candidates));   // терпимый разбор + проверка диапазона и уникальности
                if ($ranking !== null) {
                    error_log("JUDGE_OK attempt=$attempt");
                    return [array_slice(array_map(fn (int $i) => $candidates[$i - 1], $ranking), 0, $topK), true];
                }
                $lastError = 'parse_failed raw=' . mb_substr($raw, 0, 200);
            } catch (\Throwable $e) {
                $lastError = $e->getMessage();
            }
            $system = Prompts::SYSTEM_JUDGE_STRICT;                             // повтор с более строгим промптом
        }
        error_log("JUDGE_FALLBACK_PASSTHROUGH reason=$lastError");
        return [array_slice($candidates, 0, $topK), false];                     // запасной путь: исходный порядок, не падение
    }
}
Это те же приёмы, что в уроке 4: повтор для сбоя, который может пройти (судья ответил не тем форматом), и запасной путь вместо падения всей цепочки (judge_used: false, кандидаты в исходном порядке). Число повторов задаёт переменная окружения JUDGE_MAX_RETRIES, по умолчанию два.

Судья это модель, которой в промпте объясняют критерии и просят вернуть только JSON со списком номеров кандидатов в порядке убывания релевантности. Судье показывают порядковый номер и текст фрагмента (не длиннее пятисот символов), а идентификаторы файлов не показывают: так модель отвечает короткими целыми числами и не путает номер с длинным шестнадцатеричным идентификатором.

Ты — эксперт-ранжировщик поисковых результатов. Тебе дан запрос пользователя и список из N документов-кандидатов.
Оцени релевантность каждого документа запросу по 4 критериям:
1) точное совпадение темы, 2) полнота ответа на запрос, 3) фактическая обоснованность,
4) отсутствие шума и нерелевантных деталей.
Верни СТРОГО JSON вида {"ranking": [id1, id2, ...]} — где ID это ЦЕЛЫЕ ЧИСЛА от 1 до N
(номера документов из списка, НЕ file_id и НЕ hex-строки), в порядке УБЫВАНИЯ релевантности.
Никаких пояснений, markdown, тегов, текста до или после JSON. Каждый ID должен присутствовать ровно один раз.

(строгая версия для повтора добавляет:)
ОТВЕТ ДОЛЖЕН БЫТЬ ВАЛИДНЫМ JSON И НАЧИНАТЬСЯ С '{' И ЗАКАНЧИВАТЬСЯ '}'. НЕ добавляй markdown-обёртки.

Ответ судьи нельзя принимать на веру. Модель иногда оборачивает JSON в разметку или пишет номера в кавычках, поэтому функция разбирает ответ терпимо, проверяет, что номера лежат в диапазоне от единицы до числа кандидатов и не повторяются, а недостающие дописывает в исходном порядке. Если ответ всё равно не разобрался, rerank повторяет вызов с более строгим промптом.

{
  "results": [
    { "text": "...", "source_index": "fvtt...", "filename": "podpiska.md", "score": 0.87, "file_id": "fvt..." }
  ],
  "candidates": 9,
  "discovered_indexes": 3,
  "judge_used": true,
  "elapsed_ms": 5658
}

Судья меняет только порядок, а поле score приходит из поиска. Целиком функция лежит в папке с кодом занятия на Яндекс Диске в каталоге reranker: основной файл index.py, настройки config.py, поиск индексов discovery.py, поиск по ним retrieval.py, судья judge.py, промпты prompt.py, тесты разбора ответа судьи и README с командами развёртывания.

Целевая цепочка на YaWL

Та же цепочка целиком. В угловых скобках значения, которые подставляются свои.

yawl: "0.1"
start: select_recent_tickets
steps:
  select_recent_tickets:
    databaseQuery:
      connection:
        type: YDB
        host: ydb.serverless.yandexcloud.net
        port: 2135
        database: <путь к базе YDB>
        ssl: true
        iam: true
      query: |
        SELECT id, user_id, category, text, created_at
        FROM tickets
        WHERE status = 'open'
          AND created_at > CurrentUtcTimestamp() - Interval('PT24H')
        ORDER BY created_at DESC
        LIMIT 20;
      mode: QUERY
      output: '\({"tickets": .ResultSets[0]})'
      next: check_non_empty
  check_non_empty:
    switch:
      choices:
        - condition: .tickets | length > 0
          next: retrieve_kb
        - condition: "true"
          next: finish_empty
  retrieve_kb:
    httpCall:
      method: POST
      # адрес закрытой функции reranker
      url: 'https://functions.yandexcloud.net/<ID функции reranker>'
      headers:
        Content-Type: application/json
        Authorization: 'Api-Key \(lockboxPayload("<ID секрета функции>"; "api_key"))'
      # Собираем запрос из тикетов: "category: text | category: text | ..."
      body: '\({"query": (.tickets | map(.category + ": " + .text) | join(" | ")), "top_k": 5})'
      # httpCall с Content-Type: application/json отдаёт в output уже распарсенный объект
      output: '\({"kb_results": .})'
      next: build_digest
  build_digest:
    aiStudioAgent:
      promptTemplateId: <ID агента>
      message: '\("Сформируй краткий дайджест для оператора Help Desk из двух частей. " + "Часть 1 (недавние обращения): 3-5 предложений, что за тикеты пришли за 24ч, какие категории преобладают, сколько открыто. " + "Часть 2 (база знаний): для самых частых категорий тикетов найди релевантные статьи KB в выдаче ниже и кратко (1-2 строки на статью) опиши как каждая помогает. " + "Если KB-выдача пуста — Часть 2 пропусти. " + "Тикеты: " + (.tickets | tostring | .[0:3000]) + ". KB-выдача (reranker, JSON): " + (.kb_results | tostring | .[0:3000]))'
      auto_approve: true
      output: '\({"digest": .Result})'
      next: notify_operator
  notify_operator:
    telegramBot:
      token: \(lockboxPayload("<ID секрета>"; "token"))
      sendMessage:
        chatId: '<chat_id>'
        text: \(.digest)
      output: '\({})'
      next: finish_ok
  finish_empty:
    success: {}
  finish_ok:
    success: {}

Готовая цепочка подключается узлом в другие workflow или как MCP-инструмент к текстовому агенту. Это та самая вложенность из урока 2, в виде двух кнопок интерфейса.

Осторожно

Кодинговым агентам можно поручить работу с облаком, включая хранилище и архивы, но известны случаи, когда агент вычищал проект целиком. Держите всё под git: и код, и данные для поисковых индексов. Тогда любое разрушительное действие откатывается одной командой.

Что понадобится заранее

Тренажёр на странице работает без облачного аккаунта. Для самостоятельного запуска понадобится облачный каталог с биллингом: модель, функция и хранилище используют тарифицируемые ресурсы. Подготовьте каталог и сервисный аккаунт с ролями на Cloud Functions, YDB, поисковые индексы и языковые модели. К этому пять заготовок, подготовка каждой описана ниже.

  • Два поисковых индекса с меткой reranker=true
  • Развёрнутая Cloud Function reranker. Её сервисному аккаунту нужны роли ai.assistants.viewer (поиск индексов) и ai.languageModels.user (вызов модели). Для вызова оставьте функцию приватной. Создайте отдельный сервисный аккаунт с ролью functions.functionInvoker на эту функцию. Его API-ключ с областью yc.serverless.functions.invoke сохраните в Lockbox под именем api_key. Затем аккаунту workflow дайте lockbox.payloadViewer на этот секрет
  • База YDB с таблицей tickets и несколькими открытыми тикетами за последние сутки
  • Текстовый агент AI Studio для сводки. Его идентификатор подставляется в promptTemplateId
  • Учебный Telegram-бот и chat_id чата, где вы уже написали боту. Токен от BotFather сохраните в секрете Yandex Lockbox под ключом token. Сервисному аккаунту workflow выдайте роль lockbox.payloadViewer на этот секрет

Подготовка окружения

Индексы

Писать тексты базы знаний с нуля не нужно: в качестве корпуса берётся справочник help.hexlet.io. Отобраны три раздела: «Старт», «Оплата», «Ошибки кода», всего 24 статьи. Материал уже выгружен и очищен, ссылки в конце урока.

  1. Скачайте базу знаний Архив или уже распакованная папка, это одно и то же. Внутри 24 файла .md в трёх папках: start/ (8), payments/ (8), code-errors/ (8).
  2. Откройте «AI Search → Поисковые индексы» и нажмите «Создать поисковый индекс» Нужно создать два индекса: hexlet-start-payments из папок start/ и payments/ (16 файлов) и hexlet-code-errors из папки code-errors/ (8 файлов).
  3. Заполните поля
    • Имя индекса, как выше.
    • Описание: коротко о содержимом, например «База знаний help.hexlet.io про старт и оплату». Описание помогает подбирать ответы, не пропускайте.
    • Файлы: перетащите нужные .md. Поддерживаются .md, .txt, .pdf, .jsonl и другие; лимиты до 10 000 файлов и до 128 МБ на файл. Файлы автоматически режутся на фрагменты (chunks) и векторизуются.
    • Альтернатива: файл hexlet-kb.jsonl можно залить через «Загрузить подготовленные чанки», тогда индекс построится по готовому разбиению.
    • В «Расширенных настройках» для старта подойдут значения по умолчанию: размер чанка 1024 токена, перекрытие 512, эмбеддеры text-search-doc и text-search-query.
  4. Нажмите «Создать» и дождитесь статуса Completed После этого во вкладке «Файлы индекса» видны загруженные файлы и их идентификаторы.
  5. Поставьте на оба индекса метку reranker=true Скопируйте идентификаторы двух созданных индексов в переменные ниже. Пример читает текущие метки каждого индекса, добавляет reranker и проверяет результат ответа. Для вызова нужны IAM_TOKEN и FOLDER_ID в окружении. Методы Get и Update в описании API
    <?php
// Для проекта с symfony/http-client.
use Symfony\Component\HttpClient\HttpClient;

$client = HttpClient::createForBaseUri('https://rest-assistant.api.cloud.yandex.net', [
    'headers' => ['Authorization' => 'Bearer ' . getenv('IAM_TOKEN'), 'x-folder-id' => getenv('FOLDER_ID')],
]);
foreach (['<ID hexlet-start-payments>', '<ID hexlet-code-errors>'] as $id) {
    $path = '/assistants/v1/searchIndex/' . rawurlencode($id);
    $index = $client->request('GET', $path)->toArray();
    $labels = $index['labels'] ?? [];
    $labels['reranker'] = 'true';
    $updated = $client->request('PATCH', $path, [
        'json' => ['updateMask' => 'labels', 'labels' => $labels],
    ])->toArray();
    echo $updated['id'], ' reranker=', $updated['labels']['reranker'], PHP_EOL;
}

Реранкер

Разверните функцию reranker из каталога reranker в папке с кодом занятия, следуя README рядом с кодом. После развёртывания проверьте, что она находит оба индекса, и прогоните контрольные запросы.

yc serverless function invoke reranker --data '{"query":"как оплатить подписку","top_k":5}'

В ответе discovered_indexes равно двум, results не пуст, а первой стоит статья по теме запроса. Контрольных запросов шесть, и для каждого первой в выдаче должна стоять статья из указанного раздела.

База тикетов

В консоли управления откройте свою базу YDB и выполните запрос на создание таблицы. Схема взята из учебного проекта: у тикета есть категория, статус и время создания.

CREATE TABLE tickets (
  id           Utf8,        -- UUID
  user_id      Utf8,        -- Telegram chat id
  category     Utf8,        -- bug | docs | feature | access
  status       Utf8,        -- open | answered | escalated | closed
  text         Utf8,        -- текст обращения (после маскирования персональных данных)
  created_at   Timestamp,
  updated_at   Timestamp,
  PRIMARY KEY (id),
  INDEX tickets_by_user GLOBAL ON (user_id)
);

Затем добавьте несколько тикетов. Запрос шага берёт открытые тикеты за последние сутки, поэтому время создания ставится текущее.

UPSERT INTO tickets (id, user_id, category, status, text, created_at, updated_at) VALUES
  ('t-001', '100500', 'access', 'open', 'Не приходит код подтверждения при входе в аккаунт', CurrentUtcTimestamp(), CurrentUtcTimestamp()),
  ('t-002', '100501', 'docs',   'open', 'Как оплатить подписку картой, если я не в России', CurrentUtcTimestamp(), CurrentUtcTimestamp()),
  ('t-003', '100502', 'bug',    'open', 'Тесты проходят локально, а в Хекслете падает AssertionError', CurrentUtcTimestamp(), CurrentUtcTimestamp());

Агент для сводки

Агент нужен только чтобы собрать сводку, поэтому инструменты ему не подключают. Откройте «Agent Atelier → Текстовые агенты → Создать агента» и заполните три поля: имя (например, «Сводка для оператора»), модель (рядом настройки: формат ответа, температура, для фактовых ответов ставьте пониже, например 0.3, максимум токенов в ответе, обрезание контекста) и инструкцию:

Напиши короткую сводку на русском. Сначала скажи, сколько тикетов и какие категории преобладают,
затем для самых частых проблем назови подходящую статью. Если статей нет, пропусти эту часть.

Идентификатор агента берётся на его странице, и именно он подставляется в promptTemplateId. Интерфейс AI Studio периодически обновляется, при расхождениях сверяйтесь с документацией.

Проверка подготовки

  • Оба индекса в статусе Completed и с меткой reranker=true
  • Функция reranker на шести контрольных запросах возвращает discovered_indexes = 2 и статью из нужного раздела первой
  • В таблице tickets есть открытые тикеты, созданные за последние сутки
  • Агент для сводки отвечает в окне тестирования на любой запрос

Сборка по шагам

  1. Создайте workflow В AI Studio откройте раздел «Workflows» в группе Agent Atelier. Нажмите кнопку создания и задайте имя без нижнего подчёркивания. Создайте цепочку из спецификации YaWL (вставьте YAML из раздела «Целевая цепочка» со своими значениями) или оставьте пустую и собирайте шаги по порядку ниже. Результат одинаковый. Если шаг позже падает с кодом 403, причина в правах сервисного аккаунта, от имени которого идёт запуск: чинить права, а не повторять шаг.
  2. Настройте запуск Проверьте ручной запуск кнопкой «Запустить»: входные данные не нужны, достаточно {}. Добавьте расписание, например раз в день утром: время задаётся вместе с часовым поясом. Выдайте сервисному аккаунту две роли на этот workflow: serverless.workflows.executor и serverless.workflows.viewer. Без первой запуск отклоняется ошибкой can't invoke workflow, без второй doesn't have get permission for workflow. Обе приходят с кодом 400 и выглядят как неверные данные запроса, хотя причина в правах.
  3. Прочитайте тикеты и поставьте условие на данные Добавьте шаг databaseQuery с подключением к своей базе и запросом открытых тикетов за сутки (не больше двадцати). В output сохраните результат под именем tickets. Добавьте шаг switch с проверкой .tickets | length > 0, а ветку «нет» замкните на success. Условие смотрит на то, что вернул запрос, поэтому работает и при ручном запуске, и по расписанию.
  4. Добавьте вызов Cloud Function Шаг httpCall методом POST на адрес закрытой функции reranker. Укажите тип содержимого application/json и возьмите ключ для заголовка Authorization из Lockbox, как в примере выше. Тело: склейте категорию и текст каждого тикета в одну строку и добавьте "top_k": 5. Результат сохраните как kb_results. Для цепочки это один шаг с одним входом и выходом.
  5. Добавьте вызов агента Шаг aiStudioAgent, в promptTemplateId идентификатор агента. В message соберите запрос из тикетов и найденных статей, обрезав каждую часть до трёх тысяч символов выражением .[0:3000], чтобы запрос поместился в окно контекста. Результат из поля Result сохраните как digest. Поле auto_approve: true нужно, чтобы запуск не ждал подтверждения человека.
  6. Отправьте результат в Telegram Добавьте шаг telegramBot с действием sendMessage. Для token укажите ссылку на секрет Lockbox, для chatId — номер учебного чата, для text — поле .digest. Пример Yandex Cloud
    Про входящие сообщения из Telegram

    Обратное направление, webhook из Telegram в Яндекс Облако, может не заработать. Тогда входящие сообщения забирают методом pull: функция по таймеру раз в минуту опрашивает getUpdates. Пример такого опроса лежит в папке с кодом занятия в файле telegram_poller.py. Это ровно выбор «источник умеет push, но push нельзя использовать в вашей инфраструктуре» из урока 3.

  7. Запустите и разберите журнал Нажмите «Запустить» с пустым входом {}. После завершения откройте вкладку «Запуски» и раскройте запуск: список шагов, статус каждого, вход и выход, время выполнения. Подробности есть и во вкладке «Логи». Это и есть отладка по входу и выходу из урока 5: при сбое сразу видно, какой шаг упал и с какими данными к нему пришли.
  8. Переиспользуйте цепочку Два способа. В другом workflow добавьте узел «Workflow» и выберите собранную цепочку: финальный шаг внутренней обязан возвращать данные, иначе внешняя получит пустой вход. Или в разделе «MCP-серверы» создайте сервер типа «MCP-сервер с Workflows», выберите цепочку и подключите сервер к текстовому агенту.

    Для переиспользования удобна маленькая цепочка kb_search: принимает query, вызывает функцию reranker и возвращает один найденный документ или null. Выражение в output гарантирует, что внутренняя цепочка всегда возвращает данные.

    yawl: "0.1"
start: retrieve_kb
steps:
  retrieve_kb:
    httpCall:
      method: POST
      url: 'https://functions.yandexcloud.net/<ID функции reranker>'
      headers:
        Content-Type: application/json
        Authorization: 'Api-Key \(lockboxPayload("<ID секрета функции>"; "api_key"))'
      body: '\({"query": .query, "top_k": 1})'
      # results[] уже распарсен. Если пустой массив — document: null.
      output: '\({"document": (.results[0] // null)})'
      next: finish_ok
  finish_ok:
    success: {}

    Описание этой цепочки для агента (когда её вызывать, схемы входа и выхода, примеры, поведение на границах) лежит в файле kb_search_workflow.tool.md в папке занятия. Там, например, сказано, что агент должен считать document: null успешным пустым результатом и не повторять вызов.

Проверка сборки

  • Ручной запуск с пустым входом при наличии открытых тикетов доходит до конца, сообщение приходит в Telegram
  • Запуск при пустой выборке завершается на условии, не тратя вызов функции и токены
  • Запуск по расписанию без ручного ввода находит те же тикеты и отправляет сообщение
  • Вложенный вызов из внешнего workflow получает данные, а не пустой вход

Задания

Заданий три, сложность растёт от первого к третьему.

Задание 1. Минимальная цепочка с отправкой в Telegram

  1. Создайте workflow из трёх шагов: ручной запуск, вызов облачной функции (подойдёт любая готовая, например поиск по репозиторию GitHub) и HTTP-шаг отправки в Telegram.
  2. Свяжите шаги и передайте выход функции в текст сообщения.
  3. Запустите кнопкой «Запустить» и дождитесь сообщения.

Зачем: пройти полный цикл на минимальной цепочке: шаги, связи, передача данных между шагами, проверка запуском из интерфейса. Ожидаемый результат: по клику приходит сообщение в Telegram с результатом работы функции.

Задание 2. Условие, расписание и вложенность

  1. Поставьте после чтения данных шаг switch: при пустой выборке цепочка завершается сразу.
  2. Переведите запуск на расписание раз в день.
  3. Подключите готовый workflow узлом во второй, внешний workflow. Финальный шаг внутреннего должен явно возвращать данные.

Зачем: отработать три механики, на которых держатся рабочие цепочки: защита от пустых запусков, регулярный запуск без входных данных, вложенность. Ожидаемый результат: внешний workflow по расписанию вызывает внутренний, пустая выборка не порождает вызовов функции и модели, во вкладке «Запуски» видны оба уровня.

Задание 3. Устойчивая цепочка

  1. Для шага с функцией reranker добавьте политику повторов: экспоненциальная пауза плюс случайный сдвиг. Шаг только читает данные, поэтому повтор безопасен. Для отправки в Telegram повторы ограничьте: при повторе оператору придёт два одинаковых сообщения.
  2. Разведите реакции по кодам. На 401 и 403 повторов нет: причина в ключе или правах, ошибка уходит в лог. На 429 и 5xx шаг повторяется с паузой и сдвигом, а если ответ содержит Retry-After, ждёт столько, сколько в нём указано. Переполнение окна контекста повторами не лечится: на такую ошибку вход уменьшается, например в запрос к агенту передаётся вдвое меньше тикетов или вдвое короче текст каждого.
  3. При недоступности основной модели переключайте вызов на запасную, проверив, что она совместима по поддержке структурированного вывода, окну контекста и качеству.
  4. В лог каждого шага пишите идентификатор запуска, trace ID, время, код ошибки и расход токенов.

Зачем: разные сбои требуют разной реакции, а без логов с расходом токенов инцидент не разобрать. Ожидаемый результат: при искусственно вызванных сбоях (неверный ключ, урезанный лимит) цепочка не падает молча, а в журнале видны повторы, смена модели и построчный расход токенов.

Подсказки к заданию 3
  • Политика повторов в YaWL задаётся на уровне цепочки и переопределяется у шага: категории ошибок, число попыток, начальная задержка, коэффициент роста, максимальная задержка и шаг, куда перейти после исчерпания попыток. Смотрите пример в уроке 4 и документацию сервиса.
  • Ветку по коду ошибки удобно сделать шагом switch после шага с ошибкой: условие на поле с кодом, дальше либо повтор, либо шаг с логом, либо шаг с уменьшенным входом.
  • Запасная модель это второй агент AI Studio с другой моделью и той же инструкцией. Шаг switch после неудачи основного вызова переводит на него.
  • Искусственные сбои: подставьте неверный токен бота (401), уберите роль у сервисного аккаунта (403), передайте в агента весь текст без обрезки .[0:3000] (переполнение).

Проверьте себя

1. Что делает выражение \({"tickets": .ResultSets[0]}) в поле output?
  • Удаляет тикеты
  • Кладёт первую таблицу результата запроса в состояние под именем tickets
  • Проверяет, что тикеты есть
  • Отправляет тикеты в Telegram
2. Почему условие switch смотрит на .tickets, а не на вход запуска?
  • Так быстрее
  • Чтобы одинаково работать при ручном запуске с пустым входом и по расписанию
  • Вход запуска недоступен
  • Это требование YAML
3. Зачем цепочке функция reranker, если есть поисковый инструмент агента?
  • Функция быстрее
  • Агент работает только с одним индексом, а функция обходит все и выбирает лучшее
  • Поиск агента платный
  • Функция не нужна
4. Что вернёт функция, если судья дважды ответил не тем форматом?
  • Ошибку 500, цепочка упадёт
  • Кандидатов в исходном порядке с judge_used: false
  • Пустой список
  • Случайный порядок
