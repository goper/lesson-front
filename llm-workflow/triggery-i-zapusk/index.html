Запуск: триггеры и режимы выполнения

Выбрать, откуда цепочка узнаёт о работе (push, pull, расписание, кнопка) и должен ли вызывающий ждать ответа.

Две цепочки, обе написаны правильно

В одном проекте живут две цепочки. Первая проверяет изменения в коде и запускается опросом раз в пятнадцать минут. Разработчик успевает уйти на обед раньше, чем придёт комментарий. Вторая собирает сводку обращений и запускается на каждое новое обращение. За день она делает двести запусков, а руководитель читает результат один раз утром.

Обе цепочки написаны правильно. Неправильно выбран момент запуска. Это отдельное архитектурное решение, которое структура цепочки не закрывает.

Простыми словами

Есть четыре способа узнать, что пора работать. Дверной звонок: гость сам нажал кнопку (push). Выглядывать в окно каждые пять минут, не пришёл ли кто (pull). Будильник на 9:00 (расписание). Кто-то попросил прямо сейчас (ручной запуск). Звонок удобнее, но он есть не у каждой двери, а если выглядывать в окно слишком часто, ничего другого делать не успеешь.

Главная мысль

Trigger (триггер) это событие, команда или условие, которое начинает новый запуск цепочки. Execution (запуск) это один конкретный проход: десять новых pull request порождают десять независимых запусков одной и той же цепочки.

У триггера две работы: определить, когда начинать, и передать цепочке начальные данные.

Push: источник сам стучится

При push источник сам отправляет событие. Обычно это webhook: HTTP-запрос, который внешняя система посылает на заранее зарегистрированный адрес вашей системы.

Условий у push два, и оба внешние. Источник должен уметь отправлять события, а принимающая сторона должна иметь доступный извне адрес. И есть третье обстоятельство: одно и то же событие вполне может прийти дважды (сеть моргнула, источник не получил подтверждение и прислал ещё раз). Поэтому событие нужно уметь опознать по устойчивому идентификатору.

Приём webhook: быстро ответить, отбросить дубликат, работу отдать в фон
<?php
// Push: источник сам присылает событие. Одно и то же событие может прийти дважды,
// поэтому запоминаем его идентификатор и второй раз цепочку не запускаем.
use Doctrine\DBAL\Connection;
use Symfony\Component\HttpFoundation\{Request, Response};
use Symfony\Component\Routing\Attribute\Route;

final class GithubWebhookController
{
    public function __construct(private Connection $db) {}

    #[Route('/webhooks/github', methods: ['POST'])]
    public function __invoke(Request $request): Response
    {
        // Подпись GitHub проверена до вызова этого обработчика.
        $id = $request->headers->get('X-GitHub-Delivery');
        if (!$id) return new Response('missing delivery id', 400);
        $event = $request->toArray();
        if ($request->headers->get('X-GitHub-Event') !== 'pull_request' || ($event['action'] ?? null) !== 'opened') {
            return new Response('ignored', 202);
        }

        // PostgreSQL: id — первичный ключ. Строка таблицы и есть задание для фонового обработчика.
        $added = $this->db->executeStatement(
            'INSERT INTO review_jobs (id, repository, pr_number) VALUES (?, ?, ?) ON CONFLICT (id) DO NOTHING',
            [$id, $event['repository']['full_name'], $event['pull_request']['number']],
        );
        return $added ? new Response('accepted', 202) : new Response('duplicate', 200);
    }
}
Пример для события pull_request.opened. Фоновый обработчик читает сохранённые задания. Ответ об успехе отдаём после записи. Если отдельно пометить доставку полученной, а потом попытаться поставить задание в очередь, сбой между этими действиями потеряет работу.

Правила повторной доставки зависят от источника. GitHub отмечает неудачную доставку, но автоматически её не повторяет. Повтор можно запустить вручную или собственным скриптом. Обработка неудачных доставок в GitHub

Пример: Telegram умеет и push, и pull

Telegram Bot API поддерживает webhook (Telegram сам шлёт сообщения на ваш адрес) и getUpdates (вы сами спрашиваете, что нового). Выбор есть не всегда: если ваш сервер не доступен из интернета или входящие запросы к нему режет сеть, остаётся только опрос. Так бывает, например, при запуске внутри облачных функций в закрытой сети: тогда функция по таймеру раз в минуту вызывает getUpdates.

Pull: вы сами спрашиваете

При pull инициатором становится ваша система. Периодический опрос источника называют polling.

Pull нужен, когда внешний сервис не умеет push или push нельзя использовать в вашей инфраструктуре. Он же удобен, когда данные всё равно собираются пачками. Плата за pull это лишние запросы, и она регулируется одним параметром: интервалом. Чем короче интервал, тем ниже задержка и тем выше нагрузка на источник. Период выбирают по требованиям бизнеса и лимитам API, а не по ощущению.

Опрос с курсором: не читать одно и то же дважды
<?php
// Pull: мы сами спрашиваем источник. Запоминаем курсор (докуда дочитали), чтобы не брать старое дважды.
use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Console\Command\Command;
use Symfony\Component\Console\Input\InputInterface;
use Symfony\Component\Console\Output\OutputInterface;
use Symfony\Component\Messenger\MessageBusInterface;
use Symfony\Component\Scheduler\Attribute\AsCronTask;

#[AsCommand('app:poll-source')]
#[AsCronTask('* * * * *')]   // раз в минуту: интервал задаёт и задержку, и нагрузку на источник
final class PollSourceCommand extends Command
{
    public function __construct(
        private SourceClient $source,          // обёртка над GET /events?after=<id>
        private CursorStore $cursors,          // курсор хранится в базе: после перезапуска не перечитываем всё
        private MessageBusInterface $bus,
    ) { parent::__construct(); }

    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        $after = $this->cursors->get('source');
        $fresh = $this->source->fetchSince($after);

        if ($fresh === []) {
            $output->writeln('опрос: пусто (запрос потрачен впустую)');
            return Command::SUCCESS;
        }
        foreach ($fresh as $event) {
            $this->bus->dispatch(new ProcessEvent($event['id'], $event['text']));
            $this->cursors->set('source', $event['id']);
        }
        return Command::SUCCESS;
    }
}

Расписание и явный запуск

Не всякая цепочка запускается событием. Запуск по расписанию закрывает отчёты, ночную обработку, периодические проверки и сборку накопленного.

Осторожно

Расписание и pull легко перепутать, а это разные вещи. Расписание отвечает только на вопрос «когда запустить». Опрос внешнего источника внутри может быть, а может и не быть.

Запуск по расписанию
<?php
// Расписание: Symfony Scheduler. Задача запускается по cron-выражению, опроса внешнего источника нет.
use Symfony\Component\Console\Attribute\AsCommand;
use Symfony\Component\Scheduler\Attribute\AsCronTask;

#[AsCommand('app:daily-digest')]
#[AsCronTask('0 9 * * 1-5', timezone: 'Europe/Moscow')]   // 09:00 по будням
final class DailyDigestCommand extends Command
{
    protected function execute(InputInterface $input, OutputInterface $output): int
    {
        $tickets = $this->tickets->openedSince(new \DateTimeImmutable('-24 hours'));   // своя база
        $this->digest->buildAndSend($tickets);                                        // цепочка: модель → проверка → Telegram
        return Command::SUCCESS;
    }
}
// Запуск планировщика: php bin/console messenger:consume scheduler_default

Пользователь тоже запускает цепочку напрямую, обычным POST /review или кнопкой в интерфейсе. В Yandex Workflows запуск стартует через API или консольную утилиту, из интерфейса, по расписанию, по HTTPS-ссылке, через API Gateway или по событию. На внутреннюю логику способ запуска не влияет: один и тот же процесс запускается разными путями, если формат входных данных совместим.

Как выбрать триггер

Правило «webhook современнее, значит всегда push» приводит ровно к тем двумстам лишним запускам из начала урока. Выбор делается по четырём свойствам задачи.

  • Насколько быстро нужен результат. Ревью, которое должно начаться сразу после открытия PR, требует push. Отчёт к утренней встрече от мгновенной реакции не выигрывает ничего.
  • Умеет ли источник отправлять события. Если API даёт только чтение, выбор сделан за вас: остаётся polling.
  • Нужно ли обрабатывать каждое событие. Новый платёж требует отдельной проверки. Обращения за день требуют одной сводки. Во втором случае запуск на каждое событие умножает вызовы модели, не добавляя пользы.
  • Возможна ли повторная доставка. Внешнее событие приходит дважды чаще, чем кажется. Триггер связывают с устойчивым идентификатором события, чтобы отличить новую работу от дубликата.

Подсказка

Заказчик почти всегда просит запуск чаще, чем ему нужно. Просьба «присылать каждое событие сразу» обычно означает «я хочу быть в курсе». Это закрывается сводкой по расписанию и стоит на порядок дешевле.

Ждать ответа или нет

Способ запуска выбран. Появляется второй вопрос, независимый от первого: должен ли тот, кто вызвал цепочку, дожидаться её завершения?

Попробуйте Сколько ждёт клиент

Задайте длительность цепочки и режим. Красная полоса показывает, сколько времени клиент сидит с открытым соединением.

Асинхронный запуск: принять, вернуть job_id, отдать результат по запросу
<?php
// Асинхронно: принять запрос, вернуть job_id, работать в фоне, результат отдавать по job_id.
use Symfony\Component\HttpFoundation\{JsonResponse, Request};
use Symfony\Component\Messenger\Attribute\AsMessageHandler;
use Symfony\Component\Messenger\MessageBusInterface;
use Symfony\Component\Routing\Attribute\Route;

final class ReviewController
{
    #[Route('/reviews', methods: ['POST'])]
    public function submit(Request $request, JobRepository $jobs, MessageBusInterface $bus): JsonResponse
    {
        $job = $jobs->create(status: 'queued', input: $request->toArray());   // таблица jobs
        $bus->dispatch(new RunReview($job->id));                                // в очередь (транспорт Messenger)
        return new JsonResponse(['job_id' => $job->id], 202);                   // клиент свободен
    }

    #[Route('/reviews/{id}', methods: ['GET'])]
    public function status(string $id, JobRepository $jobs): JsonResponse
    {
        $job = $jobs->get($id);
        return new JsonResponse(['status' => $job->status, 'result' => $job->result]);  // queued | running | done | failed
    }
}

#[AsMessageHandler]
final class RunReviewHandler   // воркер: php bin/console messenger:consume async
{
    public function __construct(private JobRepository $jobs, private ReviewPipeline $pipeline) {}

    public function __invoke(RunReview $message): void
    {
        $job = $this->jobs->get($message->jobId);
        $job->status = 'running';
        $job->result = $this->pipeline->run($job->input);   // diff → модель → проверка
        $job->status = 'done';
        $this->jobs->save($job);
    }
}

Очередь между источником и обработчиком появляется как способ пережить всплески. Тысяча событий за секунду не должна превращаться в тысячу одновременных дорогих вызовов модели: события подождут и обработаются с контролируемой параллельностью. Своя цена у очереди тоже есть: повторная доставка, удаление дубликатов и отслеживание статусов. Заводят её тогда, когда разделение приёма и обработки действительно нужно.

Подробнее: вопросы, по которым выбирают режим
  • Сколько обычно длится цепочка и насколько предсказуема её задержка?
  • Нужен ли результат пользователю прямо сейчас? Интерактивная классификация обращения и ночной разбор тысячи документов это разные сценарии.
  • Может ли процесс приостановиться в ожидании человека или внешней системы? Держать ради этого открытый HTTP-запрос неразумно.
  • Какой объём нагрузки ожидается?
  • Можно ли показать промежуточный результат? Для генеративного интерфейса streaming иногда даёт лучший опыт без перехода в фон.

На практике: ревью кода, которое стартует после открытия PR и работает несколько минут, собирается как webhook → очередь → асинхронный workflow → комментарий. Короткий фрагмент кода, отправленный в чат, обслуживается синхронным вызовом со streaming.

Главное

Главная мысль

Триггер определяет, когда появляется запуск. Режим выполнения определяет, как вызывающая сторона с этим запуском взаимодействует. Решения связанные, но независимые, и выбирать их надо по отдельности.

  1. Источник умеет отправлять события или его придётся опрашивать?
  2. Какую задержку допускает сценарий?
  3. Нужно обработать каждое событие или достаточно одного запуска со сводкой?
  4. Может ли событие прийти повторно?
  5. Должен ли пользователь ждать завершения?
  6. Нужен ли streaming?
  7. Нужна ли очередь для контроля нагрузки?

Триггер выбран, режим выбран, цепочка запускается. Остаётся вопрос, ради которого написан следующий урок: что произойдёт, когда один из шагов завершится ошибкой.

Самостоятельная работа: выберите запуск для своей цепочки
  1. Перечислите все поводы запустить вашу цепочку. Для каждого отметьте: событие приходит само или его придётся спрашивать.
  2. Для каждого повода ответьте честно: нужен результат сразу или достаточно сводки за период.
  3. Посчитайте цену. Для опроса: сколько запросов в сутки уйдёт впустую при выбранном интервале. Для события: сколько запусков в сутки создаст пиковая нагрузка. Важен порядок величин.
  4. Для каждого повода решите, ждёт ли вызывающая сторона ответа в том же запросе. Если ждёт, укладывается ли цепочка в терпимое время и что будет при превышении.
  5. Один асинхронный случай разберите до конца: как вызывающая сторона узнает результат (опрос по id, обратный вызов, сообщение в канал).
  6. Опишите, что случится при двойной доставке одного события и что нужно, чтобы работа не выполнилась дважды.
  • Перечислены все поводы запуска, у каждого указан способ получения события
  • Для каждого повода есть ответ: сразу или сводкой
  • Посчитана цена в запросах или запусках за сутки
  • Для каждого повода выбран режим с обоснованием
  • Для одного асинхронного случая описан способ узнать результат
  • Описано поведение при двойной доставке

Проверьте себя

1. Руководитель смотрит сводку по новым заказам один раз утром. Сейчас цепочка запускается webhook-ом на каждый заказ, за ночь набираются десятки запусков. Что изменить?
  • Уменьшить интервал опроса
  • Перевести на запуск по расписанию с одной сводкой за период
  • Добавить второй webhook
  • Ничего, так быстрее
2. Запуск: cron в 09:00 → взять вчерашние данные из своей базы → сформировать отчёт. Коллега называет это polling. Почему он неправ?
  • Потому что cron это push
  • Потому что опроса внешнего источника нет: расписание отвечает только «когда», а данные лежат у себя
  • Потому что отчёт формируется моделью
  • Он прав
3. Внешний сервис отдаёт данные только на чтение, webhook не поддерживает. Бизнес готов ждать результат до пяти минут. Что выбрать?
  • Push через webhook
  • Опрос (polling) с интервалом не больше пяти минут, с учётом лимитов API
  • Запуск раз в сутки
  • Отказаться от задачи
4. Цепочка согласования может ждать решения менеджера час и больше. Сейчас клиент шлёт POST и держит соединение, получая streaming-ответ. Что изменить?
  • Увеличить таймаут соединения до двух часов
  • Перейти на асинхронный режим: вернуть job_id, результат отдать опросом, callback-ом или сообщением
  • Убрать менеджера из цепочки
  • Сделать streaming быстрее
5. Внешняя система иногда присылает событие о создании PR дважды, и цепочка запускается второй раз. Что предусмотреть на уровне триггера?
  • Повторять запуск трижды для надёжности
  • Привязать триггер к устойчивому идентификатору события и отбрасывать дубликаты
  • Отключить webhook
  • Запускать цепочку только вручную
