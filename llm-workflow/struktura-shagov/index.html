Структура: шаги и граница между кодом и моделью

Разложить работу приложения на шаги с явными входами и выходами и понять, что делает код, а что модель.

Девять шагов бота, который проверяет код

Вернёмся к боту из введения. Чтобы получить комментарий к pull request, он на самом деле делает девять действий. Вызов модели среди них один. Остальные восемь это обычный код, который должен работать одинаково каждый раз.

Главная мысль

Workflow это управляемая последовательность шагов и переходов между ними. Она получает входные данные и приводит систему к результату. Шагом может быть функция, HTTP-запрос, обращение к базе, работа с очередью или действие человека. Цепочка вполне может не содержать модели вовсе.

Простыми словами

Шаг это как пост на кухне: у холодного цеха на входе овощи, на выходе нарезка. Повар за плитой не идёт сам на склад за овощами и не относит тарелки гостям. Если нарезка пришла плохая, виноват холодный цех, а не плита. Так же и здесь: у каждого шага свой вход и выход, и по ним видно, кто ошибся.

В Yandex Workflows (сервис Яндекс Облака для таких цепочек) эта идея реализована напрямую: интеграционный шаг вызывает облачную функцию, HTTP API, модель или агента, а управляющий шаг выбирает ветку, запускает цикл, параллельные действия или ожидание. В практике (урок 8) вы соберёте такую цепочку руками.

Workflow и агент решают разные задачи

Слово «агент» часто путают с workflow. Разница в одном: кто решает, что делать дальше.

Главная мысль

Если порядок действий известен заранее и определяется бизнес-логикой, задавайте его цепочкой. Если маршрут заранее не перечислить, внутри нужного шага может появиться агент. Глобальный порядок при этом остаётся под контролем приложения.

Подробнее: когда агент внутри шага действительно оправдан

Хороший пример: «расследуй инцидент». Заранее неизвестно, понадобятся ли логи, метрики, история деплоев или переписка. Агент решает по ходу. Плохой пример: «сделай ревью PR». Источники известны: diff и метаданные. Агент здесь только добавит непредсказуемость и цену, потому что будет «думать», доставать ли diff, вместо того чтобы просто его достать.

Пять шагов типового конвейера

Архитектуры у всех разные, но для большинства прикладных задач работает один образец. Копировать его буквально не нужно. Его ценность в другом: он заставляет отделить работу модели от операций, которые обязаны выполняться одинаково каждый раз.

Шаг 1. Проверка входа

Шаг отвечает на вопрос, можно ли вообще запускать обработку. Присутствуют ли обязательные поля, соответствуют ли типы ожидаемой схеме, есть ли у пользователя право на операцию, не превышен ли допустимый размер входа. Здесь же идёт подготовка: нормализация формата, очистка служебных полей, маскирование чувствительных данных. Чем раньше система отсекает заведомо плохой вход, тем меньше лишних вызовов модели и внешних сервисов она делает дальше.

Проверка входа кодом
<?php
// Шаг 1. Проверка входа: обычный код, без модели. Symfony Validator описывает правила атрибутами.
use Symfony\Component\Validator\Constraints as Assert;
use Symfony\Component\Validator\Validation;

final class ReviewRequest
{
    public function __construct(
        #[Assert\NotBlank] #[Assert\Uuid]
        public readonly string $repositoryId,
        #[Assert\Positive]
        public readonly int $pullRequestId,
        #[Assert\Length(max: 200_000)]   // не больше ~200 КБ diff
        public readonly string $diff = '',
    ) {}
}

$validator = Validation::createValidatorBuilder()->enableAttributeMapping()->getValidator();
$request = new ReviewRequest('repo-42', 0);   // заведомо плохой вход

$errors = $validator->validate($request);
if (count($errors) > 0) {
    foreach ($errors as $e) {
        echo $e->getPropertyPath(), ': ', $e->getMessage(), PHP_EOL;
    }
    exit(1);   // дальше не идём: ни diff, ни модель не нужны
}
echo "ok, можно запускать цепочку", PHP_EOL;

Шаг 2. Обогащение контекста

Обогащение добирает то, чего в запросе нет. Строки «проверь pull request» для ревью не хватает, нужны как минимум diff и данные репозитория. Данные приходят из API, базы, файлов, поиска по документам, и это отдельная инженерная задача. Отдавать этот сбор агенту незачем, когда источники известны заранее.

Главная мысль

Модель должна рассуждать над подготовленными данными, а не компенсировать их отсутствие догадками.

Обогащение: два известных источника, запросы независимы
<?php
// Шаг 2. Обогащение: достаём diff и метаданные. Источники известны заранее, агент не нужен.
use Symfony\Contracts\HttpClient\HttpClientInterface;

final class PullRequestLoader
{
    public function __construct(private HttpClientInterface $github) {}   // scoped-клиент с base_uri api.github.com

    /** @return array{diff: string, meta: array{language: ?string, default_branch: string}} */
    public function load(string $repo, int $pr): array
    {
        // Два запроса не зависят друг от друга: HttpClient отправит их параллельно,
        // пока мы не попросим содержимое.
        $diffResponse = $this->github->request('GET', "/repos/$repo/pulls/$pr", [
            'headers' => ['Accept' => 'application/vnd.github.diff'],
        ]);
        $metaResponse = $this->github->request('GET', "/repos/$repo");

        $meta = $metaResponse->toArray();

        return [
            'diff' => $diffResponse->getContent(),
            'meta' => ['language' => $meta['language'], 'default_branch' => $meta['default_branch']],
        ];
    }
}

Шаг 3. Вызов модели

На вход уходят инструкция (системный промпт), запрос и собранный контекст. Именно здесь появляется недетерминированность: при одинаковом промпте формулировка может отличаться, а содержательно неверный ответ приходит вместе с технически успешным HTTP-ответом. Рассматривать такой шаг как обычную функцию, которая при статусе 200 выдала правильный результат, нельзя. Поэтому шаг возвращает сырой текст, а проверять его будет следующий шаг.

Вызов модели возвращает сырой ответ
<?php
// Шаг 3. Вызов модели: единственный недетерминированный шаг.
// Формат запроса OpenAI-совместимый: его понимают Yandex AI Studio и большинство провайдеров.
use Symfony\Contracts\HttpClient\HttpClientInterface;

final class ReviewModel
{
    public function __construct(
        private HttpClientInterface $ai,        // base_uri провайдера + заголовок Authorization
        private string $model,                  // идентификатор модели из настроек
        private string $promptVersion = 'v14',  // версия инструкции: попадёт в логи
    ) {}

    public function review(string $diff, array $meta): string   // возвращает СЫРОЙ текст
    {
        $system = file_get_contents(__DIR__ . "/prompts/review.{$this->promptVersion}.txt");

        $response = $this->ai->request('POST', '/v1/chat/completions', ['json' => [
            'model'           => $this->model,
            'temperature'     => 0.2,
            'response_format' => ['type' => 'json_object'],
            'messages' => [
                ['role' => 'system', 'content' => $system],
                ['role' => 'user',   'content' => "Язык: {$meta['language']}\n\nDiff:\n$diff"],
            ],
        ]]);

        return $response->toArray()['choices'][0]['message']['content'];
    }
}
response_format: json_object просит модель отвечать JSON. Это снижает число ошибок формата, но не гарантирует правильность содержания.

Шаг 4. Проверка результата

Уровней у проверки два.

  • Структурная смотрит на форму: соответствует ли ответ схеме, есть ли обязательные поля, верны ли типы. Например, severity должно быть одним из low | medium | high.
  • Содержательная (бизнес-валидация) смотрит на смысл. Корректный JSON не означает корректного решения: модель вполне может вернуть поле line правильного типа со значением, которого во входном diff не было.
Две проверки: форма, потом смысл
<?php
// Шаг 4. Проверка результата: сначала форма (схема), потом смысл (бизнес-правило).
final class ReviewChecker
{
    private const SEVERITY = ['low', 'medium', 'high'];

    /** @return array{ok: bool, error?: string, value?: array} */
    public function checkSchema(string $raw): array
    {
        $obj = json_decode($raw, true);
        if (!is_array($obj))                                       return ['ok' => false, 'error' => 'не JSON'];
        if (!in_array($obj['severity'] ?? null, self::SEVERITY, true)) return ['ok' => false, 'error' => 'severity не из списка'];
        if (!is_string($obj['summary'] ?? null))                   return ['ok' => false, 'error' => 'summary не строка'];
        if (!is_array($obj['issues'] ?? null))                     return ['ok' => false, 'error' => 'issues не массив'];
        return ['ok' => true, 'value' => $obj];
    }

    /** @param int[] $diffLines */
    public function checkBusiness(array $review, array $diffLines): array
    {
        $ghost = array_filter($review['issues'], fn (array $i) => !in_array($i['line'], $diffLines, true));
        return $ghost
            ? ['ok' => false, 'error' => 'строк нет в diff: ' . implode(', ', array_column($ghost, 'line'))]
            : ['ok' => true];
    }
}

$checker = new ReviewChecker();
$diffLines = range(10, 18);
foreach ([
    '{"severity":"high","summary":"SQL без параметров","issues":[{"line":14,"text":"конкатенация"}]}',
    '{"severity":"high","summary":"лишний пробел","issues":[{"line":512,"text":"стиль"}]}',
    '{"summary":"всё ок","issues":[]}',
] as $raw) {
    $s = $checker->checkSchema($raw);
    if (!$s['ok']) { echo "схема ✗: {$s['error']}\n"; continue; }
    $b = $checker->checkBusiness($s['value'], $diffLines);
    echo 'схема ✓, смысл ', $b['ok'] ? "✓ → отправляем\n" : "✗: {$b['error']}\n";
}
Попробуйте Проверьте ответ модели сами

Подставьте готовые варианты ответа или отредактируйте JSON и посмотрите, какая проверка его поймает.

Структурированный вывод (просьба к модели отвечать строго JSON) снижает риск ошибок формата, но не заменяет программные бизнес-правила. Схема не знает, какие строки есть в diff.

Шаг 5. Доставка результата

Результат передаётся дальше: HTTP-ответом, записью в базу, сообщением, тикетом или вызовом другого API. Часть с моделью уже закончилась, а надёжность всё ещё зависит от обычной архитектуры. Если результат уходит сразу в несколько независимых систем, действия стоит разделить: успешная запись в базу и неудачная отправка уведомления это два разных исхода, и провал одного не обязан отменять другой.

Доставка в две системы: два независимых исхода
<?php
// Шаг 5. Доставка: два независимых действия → два независимых исхода.
final class Delivery
{
    public function __construct(private ReviewRepository $repo, private SlackNotifier $slack) {}

    /** @return array{db: array, slack: array} */
    public function deliver(array $review): array
    {
        $out = [];

        try { $this->repo->save($review); $out['db'] = ['ok' => true]; }
        catch (\Throwable $e) { $out['db'] = ['ok' => false, 'error' => $e->getMessage()]; }

        try { $this->slack->notify($review); $out['slack'] = ['ok' => true]; }
        catch (\Throwable $e) { $out['slack'] = ['ok' => false, 'error' => $e->getMessage()]; }

        return $out;   // запись есть, уведомление упало → повторяем только уведомление
    }
}

// В Symfony уведомление удобнее отправить сообщением через Messenger:
//   $this->bus->dispatch(new NotifySlack($review['id']));
// Тогда повтор и очередь настраиваются транспортом, а запись в базу от Slack не зависит.

Переходы, состояние и вложенность

Линейной цепочка остаётся недолго. Правила, определяющие, какой шаг выполняется следующим, называют control flow (логика переходов). Простейший вид это ветвление по условию, которое можно вычислить заранее.

Осторожно

Параллельность экономит время, но плата за неё неочевидна: заметно усложняется обработка частичных ошибок, когда одна ветка отработала, а вторая нет. Добавляйте её при реальном выигрыше по времени, а не по умолчанию.

Состояние это данные, доступные во время конкретного запуска. Один шаг кладёт в него diff, следующий берёт его для вызова модели, третий сохраняет review_result. Чем яснее контракт между шагами (кто какое поле создаёт), тем проще понять, какой компонент породил конкретное значение. В Yandex Workflows состояние запуска это JSON, который передаётся между шагами и пополняется результатом каждого.

Попробуйте Как состояние растёт по шагам

Нажимайте «Следующий шаг» и смотрите, какие поля появляются в JSON и кто их создал.

Повторяющуюся цепочку выделяют в отдельный workflow и вызывают как один шаг более крупного процесса. Выделять стоит то, у чего есть понятный контракт «вход, внутренние шаги, выход». Агентом вложенная цепочка от этого не становится: агентность определяется выбором действий моделью, а не количеством шагов внутри.

Где живёт бизнес-логика

Хороший workflow разделяет три типа решений и не путает их между собой.

Тип решенияКто выполняетПример
Детерминированное правилокод и управляющие шаги«если сумма больше лимита, нужно согласование»
Семантическая задачамодель«определи основную проблему в тексте обращения»
Динамический выбор инструментовагент«выбери, какие источники нужны для расследования»

Путаница стоит дорого в обе стороны. Правило про лимит, отданное модели, начнёт срабатывать через раз. А попытка выразить кодом «определи основную проблему» превращается в бесконечный список условий, который всё равно не покрывает реальные обращения.

Правило считает код, смысл определяет модель
<?php
// Детерминированное правило → код. Семантика → модель.
const LIMIT = 100_000;

function needsApproval(int $amount): bool          // правило: код, всегда одинаково
{
    return $amount > LIMIT;
}

function classifyIntent(string $text): string       // смысл: модель (здесь имитация ответа)
{
    $fake = ['верните деньги' => 'refund', 'где заказ' => 'delivery'];
    foreach ($fake as $needle => $intent) {
        if (str_contains(mb_strtolower($text), $needle)) return $intent;
    }
    return 'other';
}

echo '120 000 ₽ → ', needsApproval(120_000) ? 'нужно согласование' : 'без согласования', PHP_EOL;
echo '99 999 ₽ → ',  needsApproval(99_999)  ? 'нужно согласование' : 'без согласования', PHP_EOL;
echo '«Заказ 58391 пришёл мятый, верните деньги» → ', classifyIntent('Заказ 58391 пришёл мятый, верните деньги'), PHP_EOL;
Условие ветвления по возможности вычисляет код, а не модель. Иначе цепочка перестаёт быть воспроизводимой ровно там, где предсказуемость важнее всего.

Семь вопросов, которые дают структуру

  1. Какие данные приходят на вход?
  2. Что можно проверить обычным кодом до вызова модели?
  3. Каких данных не хватает и откуда их взять?
  4. Где действительно нужна работа модели?
  5. Как проверить её результат (форма и смысл)?
  6. Какое действие выполняется после проверки?
  7. Какие данные передаются между шагами?

Ответы дают структуру. Следом появляется вопрос, который структура не закрывает: когда и каким способом этот процесс должен запускаться. Это следующий урок.

Самостоятельная работа: разложите свою задачу на шаги

Возьмите любую свою задачу, где модель вызывается хотя бы раз. Если своей нет, подойдёт сборка карточки товара по описанию от поставщика.

  1. Выпишите шаги. У каждого назовите вход и выход в виде структуры с именами полей, а не словами «текст запроса». Шаг, у которого не получается назвать вход и выход, ещё не шаг.
  2. Отметьте шаги, которым модель не нужна. Обычно это проверка входа, дополнение данными из базы, проверка ответа, отправка результата. Если шагов с моделью больше, чем без, посмотрите ещё раз.
  3. Для одного шага с моделью опишите две проверки: структурную (схема) и содержательную (бизнес-правило, которое схема не поймает).
  4. Найдите место для ветвления и место для параллельного запуска. Для ветвления укажите, кто считает условие: код или модель. Для параллельного участка проверьте, что ветки независимы.
  • Все шаги выписаны, у каждого есть вход и выход со списком полей
  • Отмечены шаги, которым модель не нужна
  • Шагов без модели не меньше, чем с моделью
  • Для одного модельного шага описаны обе проверки
  • Найдено ветвление, указано, кто вычисляет условие
  • Найден параллельный участок, проверена независимость веток

Проверьте себя

1. Первый шаг отправляет repository_id в модель с просьбой проверить, что это UUID, и только потом грузит diff. Что изменить?
  • Ничего, модель справится
  • Проверять формат кодом (регулярное выражение), модель для этого не нужна
  • Грузить diff до проверки
  • Попросить модель проверить ещё и diff
2. Модель вернула 200 и JSON ровно по схеме {severity, summary, issues}, но line внутри issues в diff нет. Какой вывод делать нельзя?
  • Ответ прошёл структурную проверку
  • Нужна содержательная проверка
  • «Схема прошла, значит ответ правильный»
  • Модель может придумывать значения
3. Последний шаг записывает результат в базу и шлёт уведомление в Slack одним действием. Запись прошла, Slack упал, шаг помечен неуспешным. Как правильнее?
  • Повторить весь шаг, включая запись
  • Разделить на два независимых действия с отдельными исходами
  • Убрать уведомление
  • Писать в Slack до базы
