Конспект и вопросы для самопроверки

Вся теория курса на одной странице: словарь, шпаргалки по урокам, две схемы для выбора решения, 24 вопроса с ответами и итоговый тест.

Пользуйтесь этой страницей перед практикой и перед тем, как собирать цепочку на рабочем проекте. Ответы на вопросы самопроверки спрятаны под каждым вопросом: сначала ответьте сами, потом раскройте.

Словарь простыми словами

Workflow
Цепочка шагов с заданным порядком. Получает вход, выдаёт результат. Порядок задаёт разработчик.
Execution
Один конкретный запуск цепочки.
Шаг
Одно действие с понятным входом и выходом. Если вход и выход назвать нельзя, это ещё не шаг.
Агент
Модель, которая сама выбирает следующее действие и инструменты. Может жить внутри одного шага цепочки.
Control flow
Правила перехода между шагами: ветвления, циклы, параллельные участки.
Состояние запуска
JSON с данными, который шаги передают друг другу и пополняют.
Структурная проверка
Проверка формы ответа: поля, типы, схема.
Содержательная проверка
Проверка смысла: выполняется ли бизнес-правило, которое схема не знает.
Trigger
Событие, команда или условие, которое начинает запуск.
Push / webhook
Источник сам присылает событие HTTP-запросом на ваш адрес.
Pull / polling
Вы сами периодически спрашиваете источник, нет ли нового.
Расписание
Запуск по времени (cron). Отвечает только на вопрос «когда», опроса внутри может не быть.
Синхронно / асинхронно
Клиент ждёт результат в том же запросе / клиент получает job_id и забирает результат позже.
Streaming
Ответ приходит частями по мере генерации. Соединение открыто до конца.
Очередь
Буфер между источником событий и обработкой, чтобы пережить всплески.
Временная ошибка
Тот же запрос позже может пройти: таймаут, 429, часть 5xx. Повтор уместен.
Постоянная ошибка
Сама не пройдёт: 401, 403, 400, переполненный контекст. Чинить причину или менять вход.
Retry, backoff, jitter
Повтор; растущая пауза между попытками; случайный сдвиг паузы, чтобы клиенты не повторяли одновременно.
Окно контекста
Максимальный объём токенов, который модель принимает за один вызов.
Corrective retry
Повтор вызова модели с указанием конкретной ошибки. Ограничен по числу попыток.
Идемпотентность
Повтор той же операции не создаёт второго эффекта. Достигается ключом операции.
Частичный сбой
Часть шагов выполнилась, следующий упал. Перезапуск с начала повторит сделанное.
Fallback
Запасной способ выполнить операцию: другая модель, другой провайдер. Должен быть совместим по формату.
Error path
Заранее определённый маршрут после ошибки, когда повторы закончились.
Log / metric / trace
Отдельное событие / число во времени / шаги одного запроса с временем.
Trace ID
Сквозной идентификатор одной операции через все компоненты.
Версия промпта
Короткий идентификатор текста инструкции, который меняется вместе с ней. Без него не понять, что сломала правка.
Оценочный набор (evals)
Список входов с заранее записанным ожидаемым результатом для воспроизводимой проверки шага с моделью.
Precision / recall
Точность: насколько чисто то, что шаг выбрал. Полнота: какую долю настоящих случаев шаг нашёл.
Модель-судья
Другая модель, которая по критериям ставит балл результату там, где свойство не выразить кодом.
Базовый уровень
Результат первого прогона набора на текущей версии шага. С ним сравнивают каждую правку.

Шпаргалки по урокам

Структура (урок 2): семь вопросов

  1. Какие данные на входе?
  2. Что проверить кодом до модели?
  3. Каких данных не хватает, откуда взять?
  4. Где нужна модель?
  5. Как проверить её результат?
  6. Какое действие после проверки?
  7. Какие данные между шагами?

Запуск (урок 3): семь вопросов

  1. Источник умеет push или нужен опрос?
  2. Какая задержка допустима?
  3. Каждое событие или сводка?
  4. Может ли событие прийти дважды?
  5. Ждёт ли пользователь ответа?
  6. Нужен ли streaming?
  7. Нужна ли очередь?

Надёжность (урок 4): шесть вопросов

  1. Что здесь может пойти не так?
  2. Пройдёт ли тот же запрос позже?
  3. Безопасно ли повторять?
  4. Сколько попыток допустимо?
  5. Что после последней попытки?
  6. Для модели: прошёл ли ответ и схему, и смысл?

Логи (урок 5): минимальный набор

  • execution_id, trace_id
  • step_name, start_time, duration
  • status, attempt, error_type
  • для модели: model, prompt_version, latency, токены
  • для агента: инструмент, аргументы, число ходов
  • никогда: ключи, сырые персональные данные

Оценка (урок 6): порядок действий

  1. Назвать самые дорогие ошибки шага
  2. Собрать набор: обычные, пограничные, из инцидентов
  3. Записать ожидания до прогона
  4. Снять базовый уровень
  5. Менять по одному, сравнивать по случаям, критичные считать отдельно

Три типа решений (урок 2)

  • Правило («сумма выше лимита») → код
  • Смысл («о чём обращение») → модель
  • Выбор инструментов («что нужно для расследования») → агент

Две схемы для выбора решения

24 вопроса для самопроверки

Отвечайте развёрнуто, своими словами, с примерами. Под каждым вопросом короткий ответ для сверки.

Структура

1. Что такое workflow и какую задачу он решает? Что ломается, когда всю работу складывают в один промпт?

Управляемая последовательность шагов с явными входами и выходами. Решает задачу управляемости: шаг можно проверить, повторить, заменить. В одном промпте правка для одного случая ломает другой, непонятно, где ошибка, контекст раздувается, проверить можно только целиком.

2. Чем workflow отличается от агента? Кто решает, каким будет следующий шаг?

В цепочке порядок задаёт разработчик, модель отвечает на своём шаге. В агенте модель сама выбирает следующее действие и инструменты. Предсказуемость важнее гибкости там, где цена ошибки высока и маршрут известен заранее.

3. По какому признаку понятно, что шаг выделен правильно?

У него можно назвать вход и выход в виде структуры с полями. «Достать diff» (вход: номер PR, выход: текст diff) это шаг. «Разобраться с PR» это ещё не шаг.

4. Из каких шагов состоит типовой конвейер? Каким модель не нужна?

Проверка входа, обогащение контекста, вызов модели, проверка результата, доставка. Модель нужна только на третьем. Остальные четыре это обычный код и обращения к системам.

5. Чем структурная проверка отличается от содержательной?

Структурная проверяет форму: поля, типы, схему. Содержательная проверяет смысл. Ответ {"severity":"high","issues":[{"line":512}]} проходит схему, но строки 512 в diff нет.

6. Где должна находиться бизнес-логика? Чем плохо вычислять условие ветвления моделью?

Правила («сумма выше лимита») в коде, смысл («о чём обращение») у модели, выбор инструментов у агента. Условие ветвления моделью делает цепочку невоспроизводимой ровно там, где важнее всего предсказуемость.

Запуск

7. Чем push отличается от pull? Когда выбор сделан за вас?

При push источник сам присылает событие (webhook). При pull вы опрашиваете источник. Если API только читает и webhook не поддерживает, выбор сделан: остаётся pull.

8. Заказчик просит присылать уведомление о каждом событии сразу. Что с этим делать?

Обычно за этим стоит «хочу быть в курсе», а это закрывает сводка по расписанию: один запуск вместо сотен и на порядок дешевле. Уточнить, нужна ли реакция на каждое событие.

9. Что произойдёт, если одно и то же событие придёт дважды?

Без защиты цепочка запустится дважды и выполнит работу дважды (второй тикет, второе письмо). Триггер связывают с устойчивым идентификатором события и отбрасывают дубликаты.

10. Как выбрать между синхронным и асинхронным выполнением?

К асинхронному склоняют долгая или непредсказуемая задержка, ожидание человека или внешней системы, большая нагрузка. Клиент получает job_id, а результат забирает опросом, обратным вызовом или сообщением в канал.

11. Зачем между источником и обработкой ставят очередь? Почему streaming её не заменяет?

Очередь сглаживает всплески: тысяча событий не превращается в тысячу одновременных вызовов модели. Streaming лишь показывает ответ частями, соединение остаётся открытым, а нагрузку он не регулирует.

Надёжность

12. Каким вопросом отличают временную ошибку от постоянной?

«Пройдёт ли тот же запрос позже без изменения содержания?» Временные: таймаут, 429. Постоянные: 401, переполненный контекст. На постоянной ошибке повтор только тратит деньги: результат будет тем же.

13. Зачем к паузе между попытками добавляют случайный сдвиг?

Если все клиенты повторят через одинаковые интервалы, они ударят по сервису одновременно и устроят новую волну нагрузки сразу после первой. Jitter размазывает попытки во времени.

14. Почему ответ модели с кодом 200 может оказаться неверным? Чем corrective retry полезнее обычного повтора?

200 значит «запрос обработан», не «ответ правильный». Модель может пропустить поле, придумать идентификатор, нарушить правило. Corrective retry передаёт модели конкретную причину отказа вместо слепой перегенерации, но тоже ограничен по попыткам.

15. Что такое частичный сбой и чем опасен перезапуск после него?

Часть шагов выполнилась, следующий упал. Перезапуск с начала повторит сделанное: уйдёт второе уведомление. Нужно хранить отметки о выполненных шагах и повторять только упавший, а для изменяющих операций иметь ключ операции.

16. Зачем нужны fallback и error path, если повторы уже настроены?

Повторы заканчиваются. Fallback даёт запасной способ (совместимая модель, другой провайдер), error path определяет, что делать дальше: отложить, уведомить человека, вернуть ошибку пользователю.

Логи и отладка

17. Зачем в логах нужен сквозной идентификатор?

Без него разбор превращается в сопоставление записей по времени. С execution_id и trace_id все события одного запуска во всех компонентах находятся одним запросом.

18. Что записывают для шага с моделью сверх обычных полей? Что мешает хранить промпты целиком?

Имя модели, версию промпта, задержку, расход токенов, прошёл ли ответ схему. Хранить промпты целиком мешают персональные данные, документы и ключи внутри: логи живут дольше и доступны шире.

19. В каком порядке разбирают сломавшийся запуск? О чём говорит рост числа токенов?

Найти запуск по идентификатору; пройти по шагам сверху вниз до первого расхождения; определить тип проблемы (вход, контекст, ответ модели, после модели); проверить повторы; сохранить случай для набора. Резкий рост токенов или вызовов инструментов: лишний контекст или зацикливание.

20. Чем отладка отличается от оценки?

Отладка: почему конкретный запуск завершился неправильно. Оценка: насколько хорошо система работает на наборе сценариев. Одна не заменяет другую: по одному ответу нельзя заключить «новая модель хуже».

Оценочный набор

21. Зачем шагу с моделью оценочный набор и чем он отличается от обычного теста?

Знания модели заканчиваются на дате обучения, ответ правдоподобен, но не обязательно верен, и каждый раз чуть другой. Поэтому одной проверки мало, а сравнение с одной эталонной строкой не работает: формулировки меняются.

22. Как выбрать способ проверки для каждого свойства результата?

Точное сравнение: класс обращения. Правило в коде: валидный JSON, order_id из обращения. Оценка другой моделью: понятность, отсутствие выдумок. То, что проверяется кодом, модели не поручают: дороже и ненадёжнее.

23. Чем отличаются точность и полнота?

Точность: какая доля выбранного шагом оказалась верной. Полнота: какую долю настоящих случаев шаг нашёл. Точность важнее, когда ложное срабатывание дорого (заваливаем команду). Полнота важнее, когда дороже пропуск (возвраты теряются).

24. Каким должен быть набор и как сравнить две версии шага?

Похож на реальный поток, с пограничными случаями и случаями из инцидентов, ожидания записаны до прогона. Сравнивать по случаям, а не по среднему: среднее скрывает, что часть починилась, а часть сломалась. Между прогонами менять одну вещь, иначе непонятно, что дало прирост.

Итоговый тест по курсу

1. Что даёт разбиение работы на шаги?
  • Модель становится умнее
  • Управляемость: шаг можно проверить, повторить, заменить отдельно
  • Промпт становится короче сам
  • Ответы быстрее
2. Кто должен вычислять условие «сумма больше лимита»?
  • Модель
  • Код
  • Агент
  • Пользователь
3. Ответ модели прошёл схему. Можно ли считать его правильным?
  • Да
  • Нет, нужна ещё содержательная проверка
  • Да, если код 200
  • Да, если temperature = 0
4. Источник не умеет webhook, бизнес ждёт до 5 минут. Что выбрать?
  • Push
  • Pull с интервалом до 5 минут
  • Расписание раз в день
  • Streaming
5. Цепочка ждёт решения менеджера час. Режим?
  • Синхронно
  • Streaming
  • Асинхронно с job_id
  • Любой
6. HTTP 401 от провайдера. Повторять?
  • Да, с backoff
  • Нет, чинить ключ
  • Да, 10 раз
  • Да, после Retry-After
7. Таймаут при создании платежа. Что нужно до повтора?
  • Ничего
  • Ключ операции, чтобы не создать второй платёж
  • Увеличить таймаут
  • Сменить модель
8. Промпт больше окна контекста. Что делать?
  • Повторять с паузой
  • Уменьшать вход
  • Ждать Retry-After
  • Добавить jitter
9. Какое поле лога позволяет понять, связана ли поломка с последней правкой инструкции?
  • duration
  • prompt_version
  • trace_id
  • status
10. С чего начинается разбор инцидента?
  • С правки промпта
  • С поиска конкретного запуска по идентификатору
  • С отката модели
  • С увеличения повторов
11. Версия B даёт среднее выше, чем A. Что ещё нужно проверить?
  • Ничего, выпускать
  • Таблицу по случаям: что починилось, что сломалось, и критичные случаи отдельно
  • Публичный рейтинг
  • Цену токенов
12. Что проверяет модель-судья?
  • Валидность JSON
  • Свойства смысла: понятность, отсутствие выдумок, тон
  • Совпадение order_id
  • Длину ответа
