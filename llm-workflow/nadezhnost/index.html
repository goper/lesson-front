Надёжность: ошибки, повторы и запасные варианты

Научиться различать виды отказов и подбирать каждому свою реакцию: повтор, исправление входа, запасной путь или остановку.

Два тикета с разницей в четыре секунды

Клиент получил два одинаковых тикета. В логах видно: запрос на создание завершился таймаутом, и обработчик честно сделал повтор по правилу «при ошибке повторить». Тикет к этому моменту уже был создан. Оборвалось соединение, а не операция.

Правило «при ошибке повторить запрос» выглядит безобидным ровно до такого случая. Иногда повтор помогает, иногда впустую жжёт ресурсы, а иногда создаёт второй тикет или второй платёж.

Главная мысль

Надёжность определяется не количеством повторов, а тем, умеет ли система различать причины ошибок и выбирать под каждую свою реакцию.

Простыми словами

Вы звоните другу с просьбой. Занято: перезвонить через минуту разумно. Номер не существует: перезванивать бессмысленно, надо искать правильный номер. Друг всё сделал, но связь оборвалась на его «готово»: если вы перезвоните и попросите снова, он сделает дважды. Три разные ситуации, три разные реакции. Одно правило «не дозвонился, звони ещё» подходит только для первой.

Временная ошибка или постоянная

Перед любым повтором задаётся один вопрос: есть ли разумная вероятность, что тот же запрос через некоторое время пройдёт успешно без изменения содержания?

ОтветВид ошибкиПримерыРеакция
Давременная (восстановимая)сетевой таймаут, сервис недоступен, ограничение частоты (429), часть ошибок 5xxповтор с паузой
Нетпостоянная (невосстановимая)неверный ключ (401), нет прав (403), невалидный запрос (400), переполненный контекст моделичинить причину или менять вход; повтор бесполезен

Неверные учётные данные не станут правильными через пять секунд ожидания. Поэтому делить ошибки полезно не на «HTTP против LLM», а на восстановимые и невосстановимые.

Попробуйте Какая реакция уместна?

Для каждой ошибки выберите реакцию. Ответ объясняется сразу.

Повтор ограничивают с трёх сторон

Бесконечные попытки только добивают проблемную зависимость, а немедленный повтор добавляет нагрузку уже перегруженному сервису. Политика повторов задаёт три вещи сразу: какие ошибки повторять, сколько попыток максимум и как растёт пауза (плюс её потолок).

  • Фиксированная пауза: 1 → 1 → 1 с. Просто и грубо.
  • Экспоненциальная (exponential backoff): 1 → 2 → 4 → 8 с. Даёт сервису время подняться.
  • Экспоненциальная с jitter: к каждой паузе добавляют случайный сдвиг. Иначе все клиенты, упавшие в одну секунду, повторят тоже в одну секунду и устроят новую волну нагрузки сразу после первой.
Попробуйте Толпа клиентов и лежащий сервис

Двадцать клиентов получили ошибку одновременно. Сравните три политики: смотрите на столбики «запросов в секунду». Чем они ниже и ровнее, тем легче сервису подняться.

Повтор с экспоненциальной паузой и jitter
<?php
// Повтор с экспоненциальной паузой и jitter. Повторяем только временные ошибки и не бесконечно.
// В Symfony HttpClient это умеет RetryableHttpClient; ниже та же логика руками, чтобы было видно решение.
use Symfony\Contracts\HttpClient\Exception\HttpExceptionInterface;
use Symfony\Contracts\HttpClient\Exception\TransportExceptionInterface;

final class Retry
{
    private const RETRYABLE = [408, 429, 500, 502, 503, 504];

    public static function run(callable $fn, int $attempts = 4, int $baseMs = 200, int $maxMs = 5000): mixed
    {
        for ($attempt = 1; ; $attempt++) {
            try {
                return $fn();
            } catch (TransportExceptionInterface $e) {           // таймаут, обрыв сети → временная
                $retryable = true; $retryAfter = null; $code = 'network';
            } catch (HttpExceptionInterface $e) {                // ответ с кодом
                $code       = $e->getResponse()->getStatusCode();
                $retryable  = in_array($code, self::RETRYABLE, true);
                $retryAfter = $e->getResponse()->getHeaders(false)['retry-after'][0] ?? null;
            }
            if (!$retryable || $attempt >= $attempts) {
                throw $e;                                        // постоянная ошибка или попытки кончились
            }
            $exp   = min($maxMs, $baseMs * 2 ** ($attempt - 1));  // 200 → 400 → 800 → …
            $delay = $retryAfter !== null
                ? (int) $retryAfter * 1000                        // Retry-After важнее нашей формулы
                : random_int(0, $exp);                            // иначе jitter: случайная пауза до потолка
            error_log("попытка $attempt не удалась ($code), ждём $delay мс");
            usleep($delay * 1000);
        }
    }
}

// Готовый вариант через конфигурацию (config/packages/framework.yaml):
// framework:
//   http_client:
//     scoped_clients:
//       ai.client:
//         base_uri: '%env(AI_BASE_URL)%'
//         retry_failed: { max_retries: 3, delay: 200, multiplier: 2, max_delay: 5000, jitter: 0.3,
//                         http_codes: [408, 429, 500, 502, 503, 504] }

HTTP-код помогает, но политику не задаёт. Он подсказывает вид ошибки, а решение всё равно за вами и документацией конкретного API.

403нет правнет: чинить права, а не ждать

Ошибки, которые повтор не лечит

Переполненный контекст

Когда вход не помещается в окно контекста модели (максимальный объём токенов, который она принимает за один вызов), тот же запрос будет падать столько раз, сколько вы его отправите, просто дороже и медленнее. Лечится это изменением самой обработки: убрать лишний контекст, забрать только нужные документы, разбить данные на части, сжать историю или перейти на поиск по базе знаний (retrieval) вместо передачи всей базы.

Подсказка

Считать токены нужно средствами той модели, с которой работаете, а не по словам, по байтам или по правилам другой модели. У разных моделей разные токенизаторы.

Неверный ответ при успешном статусе

Код 200 от провайдера означает, что запрос обработан, и ничего не говорит о содержании. Модель может пропустить обязательное поле, вернуть значение не того типа, придумать идентификатор, нарушить бизнес-правило или выбрать неподходящий инструмент. Поэтому после вызова идёт отдельный шаг проверки: сначала структурная (форма), потом смысловая (содержание). Подробно эти проверки разобраны в уроке 2.

Corrective retry (исправляющий повтор) отличается от обычного тем, что модель получает конкретную причину отказа, а не просто просьбу попробовать ещё раз. Такой повтор осмысленнее слепой перегенерации, но и он ограничен по числу попыток: если модель продолжает нарушать критичное правило, шаг завершается ошибкой или уходит в запасную ветку. Программные гарантии он не заменяет: идентификаторы, права доступа и лимиты остаются на коде.

Corrective retry: повтор с указанием ошибки и лимитом попыток
<?php
// Corrective retry: повтор с указанием, что именно было не так. Число попыток ограничено.
final class ReviewWithCorrection
{
    public function __construct(private ReviewModel $model, private ReviewChecker $checker) {}

    public function run(string $prompt, int $maxAttempts = 2): array
    {
        $feedback = null;
        for ($attempt = 1; $attempt <= $maxAttempts; $attempt++) {
            $raw   = $this->model->review($prompt . ($feedback ? "\n\n$feedback" : ''));
            $check = $this->checker->checkSchema($raw);
            if ($check['ok']) {
                return $check['value'];
            }
            error_log("попытка $attempt ✗ {$check['error']} → повторяем с указанием ошибки");
            $feedback = "В прошлом ответе ошибка: {$check['error']}. Верни исправленный JSON.";
        }
        throw new \RuntimeException("модель не исправилась за $maxAttempts попытки → error path");
    }
}

Повтор безопасен не всегда

Идемпотентность это свойство операции, при котором повтор того же логического запроса не создаёт дополнительного эффекта. Прочитать данные можно сто раз, и ничего не изменится. Создать тикет сто раз это сто тикетов. Именно идемпотентности не хватало в истории с двумя тикетами: клиент не знал, что операция уже прошла, и повторил её.

Работает это через идентификатор операции, который отправляется вместе с запросом и с каждым его повтором. Принимающая система видит знакомый идентификатор и понимает, что новой операции нет, а возвращает результат старой. Если API таких ключей не поддерживает, приложение хранит собственный идентификатор или перед повтором проверяет, не создан ли результат уже.

Попробуйте Таймаут после создания: с ключом и без

Нажмите кнопку в обоих режимах и сравните, сколько тикетов окажется в системе после повтора.

Ключ идемпотентности: клиент шлёт, сервер проверяет
<?php
// Идемпотентность: повтор с тем же ключом операции не создаёт второй тикет.

// СТОРОНА КЛИЕНТА: ключ выводится из самой операции, поэтому при повторе он тот же.
final class TicketClient
{
    public function __construct(private HttpClientInterface $crm) {}

    public function create(string $prId, string $text): array
    {
        $key = 'review-pr-' . $prId;                                  // стабильный ключ операции
        return $this->crm->request('POST', '/tickets', [
            'headers' => ['Idempotency-Key' => $key],
            'json'    => ['text' => $text],
        ])->toArray();   // повтор по таймауту (см. Retry::run) уйдёт с тем же заголовком
    }
}

// СТОРОНА СЕРВЕРА (если CRM ваша): таблица tickets с UNIQUE(idempotency_key).
#[Route('/tickets', methods: ['POST'])]
public function create(Request $request, Connection $db): JsonResponse
{
    $key = $request->headers->get('Idempotency-Key');
    if ($key && ($existing = $db->fetchAssociative('SELECT id FROM tickets WHERE idempotency_key = ?', [$key]))) {
        return new JsonResponse($existing, 200);                      // уже делали: отдаём старый
    }
    $id = $this->tickets->insert($request->toArray()['text'], $key);  // UNIQUE не даст вставить дважды даже при гонке
    return new JsonResponse(['id' => $id], 201);
}
Главная мысль

Повтор безопасен только тогда, когда вы понимаете, что произойдёт при повторном выполнении операции.

Частичный сбой

Та же проблема на уровне всей цепочки. Часть шагов отработала, а следующий упал.

Поэтому многошаговый процесс хранит достаточно состояния, чтобы понимать, что уже завершено, и повторяет только нужный шаг или уходит в заранее предусмотренное восстановление.

Отметки о выполненных шагах: перезапуск пропускает сделанное
<?php
// Частичный сбой: храним, какие шаги уже завершены, и при перезапуске их пропускаем.
final class DigestRun
{
    /** @param array<string, callable> $steps имя шага → действие */
    public function __construct(private RunStateStore $state, private array $steps) {}

    public function run(string $executionId): void
    {
        $done = $this->state->load($executionId);                 // ['saveDraft' => 'draft-1', …] из базы
        foreach ($this->steps as $name => $step) {
            if (isset($done[$name])) {
                error_log("$name → уже сделано, пропускаем");
                continue;
            }
            $done[$name] = $step($done);                           // упадёт → остальное не выполнится
            $this->state->save($executionId, $done);              // отметка сразу после шага
            error_log("$name → {$done[$name]}");
        }
    }
}
// Первый запуск: saveDraft ✓, notify ✓, createTicket ✗ (CRM 503).
// Перезапуск после починки CRM: saveDraft и notify пропущены, второе уведомление не уходит.

Куда идти, когда попытки кончились

Fallback (запасной путь) это другой способ выполнить операцию, когда основной недоступен: например, запасная модель или другой провайдер. Доступность он поднимает, но только если запасной вариант совместим с требованиями. Другая модель может отличаться поддержкой структурированного вывода, вызовом инструментов, окном контекста, задержкой и качеством. Поэтому запасной путь проверяют так же, как основной. И проектируют его отдельно для каждой зависимости: недоступность CRM переключением модели не лечится.

Запасная модель с проверкой совместимости
<?php
// Fallback: запасная модель, но только совместимая по формату ответа.
final class ReviewWithFallback
{
    public function __construct(private ReviewModel $primary, private ReviewModel $fallback, private ReviewChecker $checker) {}

    public function review(string $diff, array $meta): array
    {
        try {
            return ['from' => 'primary', 'raw' => $this->primary->review($diff, $meta)];
        } catch (HttpExceptionInterface $e) {
            if ($e->getResponse()->getStatusCode() !== 503) {
                throw $e;                                              // не всякая ошибка ведёт к запасному пути
            }
            error_log('основная модель недоступна → запасная');
            $raw = $this->fallback->review($diff, $meta);
            if (!$this->checker->checkSchema($raw)['ok']) {            // запасная должна отдавать тот же формат
                throw new \RuntimeException('запасная модель несовместима по формату → error path (оператор)');
            }
            return ['from' => 'fallback', 'raw' => $raw];
        }
    }
}

Error path (маршрут ошибки) это заранее определённый путь после отказа, и он зависит от причины. Некорректный ввод возвращается пользователю сразу. Временный сбой проходит через повторы. Критичный невосстановимый уходит на ручную проверку.

В Yandex Workflows: политика повторов и маршрут ошибки

В Yandex Workflows политика повторов задаётся на уровне всей цепочки и может переопределяться для отдельных шагов. Настраиваются категории ошибок, которые повторять, максимальное число попыток, начальная задержка, коэффициент роста паузы (backoff) и максимальная задержка. После исчерпания попыток задаётся переход на другой шаг. По смыслу спецификация выглядит так (точные имена полей сверьте с документацией сервиса):

steps:
  retrieve_kb:
    httpCall:
      url: https://functions.yandexcloud.net/<id>
      # политика повторов для этого шага: только временные ошибки, 3 попытки, пауза растёт вдвое
      retryPolicy:
        errorList: [TIMEOUT, HTTP_5XX]      # какие категории повторять
        retryCount: 3
        initialDelay: 1s
        backoffRate: 2.0
        maxDelay: 30s
      # после исчерпания попыток — переход на шаг обработки ошибки, а не падение всей цепочки
      errorStep: notify_operator
      next: build_digest

Политику и маршрут ошибки проектируют вместе: политика без маршрута оставляет цепочку висеть, маршрут без политики срабатывает на первом же таймауте.

Главное

Главная мысль

Надёжная цепочка не прячет ошибки за повторами. Она сначала классифицирует сбой и только потом выбирает реакцию.

Каждый внешний и недетерминированный шаг стоит прогнать по пяти вопросам ещё на этапе проектирования. Что здесь может пойти не так? Может ли тот же запрос пройти позже? Безопасно ли повторять операцию? Сколько попыток допустимо? Что произойдёт после последней попытки? Для модели добавляется шестой: технически успешный вызов обязан пройти и структурную, и смысловую проверку, потому что код 200 о качестве ответа не говорит.

Стратегии ошибок определены. Остаётся понять, как увидеть, какой путь фактически прошёл конкретный запуск и почему он закончился именно так. Об этом следующий урок.

Самостоятельная работа: разложите отказы своей цепочки
  1. Выпишите все места, где цепочка может сломаться. Считайте не только модель, но и базу, внешние API и отправку результата.
  2. Разделите отказы на временные и постоянные вопросом «изменится ли что-то, если повторить через минуту?».
  3. Для временных задайте политику: число попыток, рост паузы, наличие случайного сдвига. Объясните, зачем нужен сдвиг.
  4. Опишите один случай, когда модель вернула 200 и валидную структуру, но неверное содержание, и проверку, которая это поймает.
  5. Для одной зависимости опишите запасной путь и проверьте, что он совместим по формату ответа.
  6. Найдите место, где первое действие уже выполнилось, а второе упало, и опишите, что нужно, чтобы перезапуск не выполнил первое дважды.
  • Выписаны все места, где цепочка может сломаться, включая базу и отправку
  • Отказы разделены на временные и постоянные
  • Для временных задана политика повтора
  • Объяснено, зачем нужен случайный сдвиг
  • Описан успех с неверным содержанием и проверка
  • Описан совместимый запасной путь
  • Найден частичный сбой и описана защита от повторного выполнения

Проверьте себя

1. В истории шага три попытки подряд с кодом 403 Forbidden и растущими паузами между ними. Что здесь уместно?
  • Увеличить число попыток и максимальную паузу
  • Добавить jitter
  • Убрать повторы для этого кода и заняться правами сервисного аккаунта
  • Переключиться на запасную модель
2. Вызов create_ticket() завершился таймаутом, но тикет во внешней системе уже создан. Цепочка собирается повторить шаг. Что сделает повтор безопасным?
  • Увеличить таймаут
  • Ключ операции (идемпотентность): по нему система узнает уже созданный тикет
  • Повторить только один раз
  • Повторить через час
3. Черновик сохранён, уведомление отправлено, создание тикета упало. Дежурный предлагает перезапустить цепочку с начала. Чем плох этот вариант?
  • Перезапуск слишком медленный
  • Первые два действия выполнятся повторно: уйдёт второе уведомление
  • Тикет всё равно не создастся
  • Ничем, это нормально
4. Модель вернула объект без обязательного поля severity, структурная проверка это поймала. Как разумно построить реакцию?
  • Сразу отправить результат дальше
  • Повтор с указанием ошибки (corrective retry), с лимитом попыток, затем error path
  • Бесконечно повторять, пока не исправится
  • Отключить проверку
5. Шаг падает с переполнением окна контекста: в промпт попадает вся база знаний. Retry policy настроена на три попытки с backoff. Что поможет?
  • Увеличить число попыток до десяти
  • Добавить jitter
  • Уменьшить вход: передавать только нужные документы (retrieval), резать и сжимать
  • Сменить HTTP-клиент
6. Зачем к экспоненциальной паузе добавляют jitter (случайный сдвиг)?
  • Чтобы повторы были быстрее
  • Чтобы клиенты не повторяли запрос одновременно и не создавали новую волну нагрузки
  • Чтобы сократить число попыток
  • Это требование HTTP
